# 地形爬升（TERRAIN CLIMB，T2）：沿墙连续爬升 + 高度上限

> 状态：`PROVISIONAL_NOT_TESTED`；设计已批准（Lead，2026-11-16；D1–D5 见 §10）。所有倍数、速度、时间标 **PROVISIONAL**（我方暂定，非原作测得值）。
> 依据：所有者手感要求（§1）、`Runtime/` 现行代码、`Docs/Research/` 的公开材料与真实地形数据、`CONTACT_MODEL_V2.md` 的爬升通道、社区/官方页线索（§4 E10–E13）。手感要求优先于二手推断。

## 0. 一句话

把「台阶能不能上」从一条**高度阈值**（`0.25·D` 的支撑带）改成**一条接触驱动的连续爬升**：推墙时球沿墙
慢慢上升，**上限 `H_cap = k_h·(2r + λL)`**（`k_h = 1.5`，PROVISIONAL），**球底越过墙顶就翻上去**、
**没越过上限就掉落**；`0.25·D` 只留作 `h<r` 棱滚越的即时特例与诊断。判据只有一处（`ClimbMath` +
`ContactClassificationMath`）：地形三角面、静态盒、道具顶、斜面**共用同一个接触集**。

## 1. 手感要求（最高优先级约束）

要求（所有者，2026-11-16）：球贴墙推进时**以有限速度上升，上升到一个高度上限后失去附着并掉落**。

三条硬约束：

1. **连续**：不是一步弹上台面；推着墙时球心以有限速度上升（有爬升速度）。
2. **有上限**：到某个高度就失去附着、受重力回落——不是无限爬、也不是到顶锁死。
3. **上限之下能翻上去**：墙顶低于上限时球应能翻上墙顶，这才解释「22 cm 球能上约 0.3 m 台阶」。

对照 [PARITY_AUDIT 的 M07/M08](../Parity/PARITY_AUDIT.md)：

* **M07（一致）**：不加爬升键，推入即爬。见 [OPEN_DECISIONS](../../OPEN_DECISIONS.md) 末段。
* **M08（不一致）**：原作证据是「无（只有'超过高度就掉回来'）」，而我方 v2 现在是
  `v_slide ≤ 1.0 m/s + 到顶锁定 + 0.35 s 冷却` 的「一次推入一次机会」。本设计把「锁定到松手」降级为
  可选项，默认改成「掉落」——见 §6.5。

**这条描述推翻了什么**：

* **方案 A（单步几何抬升）不再是主方案**：瞬间位移与「慢慢往上爬」直接冲突（§5.1 保留为特例）。
* `CONTACT_MODEL_V2.md` §2.5 的三段式原来把上限取成 **`h<0.5D 滚 / 0.5D≤h<D 爬 / h≥D 墙`**（即
  `H_cap = D`），那是把 `H_cap` 当成了墙高上限。§6.3 的几何推导给出：球底越过墙顶需要**球心上升 =
  台阶高 `h`**，所以「能翻的墙高 ≈ H_cap」；要让 0.222 m 球翻 0.30 m，`k_h` 必须 ≈1.45–1.5，不是 1.0
  （该文档已按 1.5 改）。

## 2. 现状机制：0.19 m 台阶为什么过不去（三道门，均已确认）

### 2.1 支撑带：`SupportSurfaceMath.IsStepWithinLimit`

* 判据：`rise = topY − referenceSupportHeightM; return rise <= stepLimitM`
  （`Runtime/BallLayers/TerrainSupport/SupportSurfaceMath.cs:269-278`）。
* 参照是**球底**，`stepLimit = stepHeightOverBallDiameter(0.25) × 语义直径`
  （`KatamariBallMotor.cs:117`、`:3292-3297`）。
* 地形候选的 ceiling = `ballBottom + stepLimit`（`Runtime/BallContact/TerrainMeshMath.cs:342`），
  再在球心 XZ 上过同一个谓词一次（`:375`）。
* **D = 0.222 ⇒ limit = 0.0555；0.19 > 0.0555 ⇒ 台阶顶面根本不是候选**。
* 同一谓词还产出静态盒的扫掠掩码（`KatamariBallMotor.cs:3212`、`SupportSurfaceMath.cs:968-992`）：
  判墙的盒**留在扫掠里挡路**，判台阶的盒从扫掠剔除并变成候选。

### 2.2 T1 只推不爬

* 地形穿透由接触求解按最近三角面的法线推挤处理；**竖直踢面的法线水平 ⇒ 只把球推离墙、不抬球**，抬球要靠爬升通道。
* 爬升通道在 `ContactSolveMath` 里，由 `StepContactV2` 驱动（唯一位置权威）。

### 2.3 v2 权威不查地形

* `StepContactV2` 把平面 / OBB / 道具代理与地形三角面候选一起喂 `ContactSolveMath.TryStep`（见 `TERRAIN_MESH_CONTACT.md`）。
* 能不能爬 0.19 m 台阶由 T2（地形接触进爬升通道）的实现决定，不是参数没调好。

### 2.4 判据定位（一句话）

`IsStepWithinLimit` 在「球底 + 0.25·D」处截断候选；T1 只做推出；v2 的爬升拿不到地形接触。
**要改的是第三条**（把地形接触喂进同一套爬升）与第一条的定位（降为诊断），**不是把 0.25 放大**。

## 3. 抖动 / 边缘滑走（低优先；2026-11-16 已归因）

现象：无人推动时约 **0.02 m/s** 漂移、并被台阶边缘带着走。**操作员 2026-11-16 复核：这是驱动脚本
残留输入，不是地形物理。** 本节低优先：不为它改代码；若复现，按下面两条机制查。

* **H1 探针环随视觉滚转 + 法线重贴**（推断）：支撑查询把 `visualRollRotation` 当 `localToWorld`
  （`KatamariBallMotor.cs:3397`；`TerrainMeshMath.cs:345-361`），球一转，16 个环探针扫过相邻三角形，
  「带内最高」换面（`:375-382`）⇒ `GroundContactMath` 沿新法线重贴（`GroundContactMath.cs:110-111`）
  带出水平分量（2 mm × 10° ≈ 0.35 mm/步 ≈ 1.7 cm/s）。
* **H2 T1 推出 ↔ 地面重贴的凹角循环**（推断）：T1 每次推出留 1 mm 缝（`:3465`），地面重贴再压回；
  面 id 翻转还会进 `isFalling`（`SupportSurfaceMath.cs:1161-1171`）⇒ 竖向小跳。
* **复现时的三步现场实验**（不写代码）：E1 `maxRollDisplacementM=0` 冻结视觉滚转；E2
  `terrainSupportEnabled=false`（T1 仍在）；E3 读 `[story]` 的 `supportId/supportY/gap`。
* 推荐方案（§6）本来就没有探针环与「最高者胜」，H1 在结构上不存在；§8.1 的 10 s 漂移项保留为廉价
  回归，不作为验收门。

## 5. 方案

### 5.1 方案 A：几何台阶规则（保留为「小台沿」特例）

**判据**：`rise = topY − ballBottom ≤ k_step·D ∧ pushIn ≥ p_min ∧ v_gate ≥ v_req(θ) ∧ cooldown = 0`，
满足则把台阶顶面纳入候选，用一次大抬升（`maxStepUpLiftWorldM = 0.6`，`KatamariBallMotor.cs:120`）
把球抬上去。

* **输入**：推进方向与目标速度、接触法线、台阶高 `h`、接触类别。**成本** ≈0（复用 T0，只改 ceiling）；
  **U#** 可行（纯静态数学）。
* **一致性**：与静态盒共用 `IsStepWithinLimit` 的放宽版——**但这是第二套阈值**（0.25·D 与 `k_step·D`
  并存），且斜面/道具顶没有「踢面」，只能按「顶面在带内」判，语义天生不同。
* **出错观感**：**一步位移 0.19 m**（或按 `maxStepUpLift` 一次 0.6 m）——与一手描述「慢慢往上爬」
  直接冲突；门槛两侧的球（0.249·D 与 0.251·D）一个瞬移上去、一个永远挡住，是最难调的手感。

### 5.2 方案 B：接触驱动的连续爬升（推荐）

把地形三角面接成**接触源**，与平面 / 静态盒 / 道具 / 斜面一起进 `ContactSolveMath.TryStep`；
分类、支撑、爬升通道全部复用现有实现：

* 分类：`n.y ≥ cos(45.5°)` RIDE；`n.y > −0.05` 且更陡 CLIMB；否则 NONE
  （`ContactClassificationMath.cs:48`；`ContactTuning.cs` 的 `ThetaRideDeg`）。
* 支撑 = `n.y` 最大的 RIDE 接触（并列取更深的）；墙 = 推进方向压得最狠的 CLIMB 接触；
  墙必须比支撑陡 ≥15°（`ContactClassificationMath.cs:64`）。
* 爬升：`p ≥ 0.2 ∧ v_gate ≥ v_req(θ) ∧ h < H_cap ∧ cooldown = 0 ∧ 未锁`，通道接管垂直速度
  （`ContactSolveMath.cs:594-660`）。
* **本设计新增的三条**（缺口，§2.3 的 v2 也缺）：
  * **地形接触源**（球-三角面最近点 / 法线 / 深度 / 棱-面-角特征 / 该实体的**顶面高度**）。
  * **翻越出口**：爬升的目标不是「接触消失」，而是**球底到达接触实体的顶面高度**（§6.3）；出口把球底
    **落在台沿上**（≤ 出口 slop 5 mm）并**清掉竖直速度**——出口是交棒，不是起跳（不清竖直速度时 70° 坡多出 4.6 mm 弹跳）。两条不变式：①**hang 只在已知顶面时存在**，没有顶就随接触
    消失结束（否则会把球抬到 `H_cap`，低墙实测 0.581）；②**爬升的竖直位移被夹到「离台沿还剩多少」**，
    球底永不越过台沿（实测越 5.26 mm）。
  * **上限掉落**：到 `H_cap − 0.02` 松脱 + 一点离墙速度（§6.5）。
* **一致性**：**一条规则、一个判据、一处实现**。静态盒、道具顶、斜面、地形全走同一个接触集与同一个
  `ClimbMath`；`0.25·D` 不再参与物理（v2 里它已经是诊断量）。地面平面在 v2 是**接触源**，所以「地形
  答得出 ⇒ 平面退出」由电机每步先问一次 T0（诊断带）后关掉 `hasGround` 实现（否则坑里的球会被 y=0
  的平面顶出去）。
* **测试场影响**：见 §5.4。
* **每步成本**：接触收集**复用 `terrain-support-fix` 的「每步按球足迹从网格索引收集候选三角形」**
  （不另写逐 chunk 扫描）：59 个 chunk 里只取足迹附近几块 ⇒ **≈200–800 次三角面测试/步**（含 ≤8 子步
  × 3 次推出重查）。
* **U# 可行性**：可行。新增的仍是静态方法 + 调用方数组，无分配、无结构体、无静态字段；每个子步
  **1 次** Udon 调用，不是每三角形一次。
* **出错观感**：`k_h` 太小 ⇒ 0.19 凹槽/0.3 台阶只爬一半就掉（像「墙太滑」）；太大 ⇒ 0.60 m 球能爬 0.9 m、
  1.10 m 球能爬 1.65 m 的墙（「蜘蛛球」，尺寸门的节奏坏掉）；翻越出口不做限速 ⇒ 球在棱上一帧弹起 `r`
  （0.222 球 11 cm、1.1 m 球 55 cm）。

### 5.3 两条方案的取舍（为什么选 B）

一手描述要求「连续 + 上限 + 超限掉落 + 顶低于上限可翻越」四件事。A 只能做「阈值 + 瞬移」，**第 1、2、3
条做不到**；B 的四件事全部落在已有 `ClimbMath` 上，且不需要第二套阈值。A 的 `0.25·D` 在 B 里降级为
`h<r` 的**即时特例**（棱推出，见 §6.3 第 3 段）与诊断读数。

## 6. 推荐方案（B）的规则与参数

### 6.1 状态机（每步；只有一处实现）

| 状态 | 进入 | 速度 | 退出 |
|---|---|---|---|
| 无 | 无墙接触 / 推入 < `p_min` | 正常接触求解 | — |
| **爬升** | `p ≥ 0.2` ∧ `v_gate ≥ v_req(θ)` ∧ `h < H_cap` ∧ 冷却 0 ∧ 未锁 | 垂直/沿切线的爬升通道（§6.2），**保留水平推进的"压墙"分量**（否则到顶没有前冲，见 §6.3） | 松手 / 转向 / 顶面到达 / 上限 |
| **翻上**（出口） | 球底 ≥ 接触实体顶面 − `0.005` | 正常接触 + 推进 | 落到顶面成 RIDE |
| **掉落** | `h ≥ H_cap − 0.02`，或接触消失 | 重力 + `v_slide ≤ 1.0`；上限掉落再给离墙速度 | 落地 |

### 6.2 爬升速度（回答「与推进速度 / 球径的关系」）

沿用 `ClimbMath.ClimbSpeed`（`ClimbMath.cs:88-99`）：

```
v_up(h) = clamp(p,0,1) · rate(v_gate) · (m(θ)/m(90°)) · v_up0 · sqrt(1 − h/H_cap)
v_up0   = 1.718 · H_cap / T_climb
rate    = clamp(v_gate / 2 m·s⁻¹, 0.75, 1.5)
v_gate  = max(|实际水平速度|, 0.5 · 目标速度)      # 目标速度 = 推入量 × 速度上限（ComputeDrive）
m(θ)    = cosθ + 0.15·sinθ
```

**关系**：速度 ∝ 球径（`v_up0 = 0.917·D`，m/s），∝ 推入量（0–1），∝ 目标速度（0.75–1.5×），到上限前
按 `sqrt` 衰减。**所有球径到顶时间相同**（`T_climb`），大球 m/s 上更快、身位上一致。

| D (m) | H_cap=1.5D | v_up0 (m/s) | 0.19 m 用时 | 0.30 m 用时 | 满上限用时 |
|---:|---:|---:|---:|---:|---:|
| 0.222 | 0.333 | 0.204 | **1.1 s** | 2.3 s | 2.81 s |
| 0.30 | 0.45 | 0.275 | 0.8 s | 1.4 s | 2.81 s |
| 0.60 | 0.90 | 0.550 | — | 1.4 s | 2.81 s |
| 1.10 | 1.65 | 1.008 | — | 0.31 s | 2.81 s |
| 2.20 | 3.30 | 2.016 | — | 0.15 s | 2.81 s |

（满推、`pushIn=1`、`rate=1.0`；用时 `t = 1.164·T_climb·(1 − sqrt(1 − h/H_cap))`。）

### 6.3 上限与「翻上去」的几何（关键推导，决定 `k_h`）

球半径 `r`，竖直踢面高 `h`，球在地面上时球心高 `r`。

1. **球底越过墙顶** ⇒ 球心要 `h + r` ⇒ **球心上升量 = `h`**；⇒ **能翻上去 ⇔ `H_cap > h`**
   （含 0.02 m 到顶余量：`H_cap > h + 0.02`）⇒ 最大可翻墙高 ≈ `H_cap = k_h·D`。
2. **0.222 m 球翻 0.30 m ⇒ `k_h ≥ (0.30+0.02)/0.222 = 1.44`**；0.19 m 凹槽只要 0.86。
3. **为什么必须由爬升通道接管最后这段**：不接管的话，最后 `r` 的抬升只能来自墙顶棱的推出，而推出量
   = 穿透深度，**可以在一帧内到 `r`**（0.222 球 11 cm、1.10 m 球 55 cm）。所以出口判据必须是
   「球底到达实体顶面」，不能用「接触消失」。
4. **陡坡**：球在坡上时球底比接触点低 `(1−n.y)·r`（70° ≈0.66r，90° = r），出口同理，但「顶」是
   坡顶台面；多三角面的坡不会在每片顶早退（球底恒低于接触点），只有到台面才触发。
5. **特例 `h < r`**：球心一开始就高于墙顶，棱接触法线自带 +Y 分量，推出直接把它滚上去——
   这就是 `0.25·D` 台阶带现在「恰好能用」的那一段，也是 A 的正确用例。
6. **`contactTopY` 的三角剖分敏感（已知限制）**：台沿取**命中三角形的最高顶点**。对干净的轴对齐台阶
   精确；横切成两段的竖墙会给出**假低位**台沿（提前出口 → 重新起爬，终态仍对但有一次顿挫），
   斜顶/倒角给出**假高位**（多爬一截再落，受 `H_cap` 封顶），跨折痕的长三角形同样不保证。
   §8.1 的 SplitRiser / ChamferedStep 两条就是钉这个的；**两条在 Unity 里跑过之前，翻越出口不算验证**，
   届时若红，退化路径是关掉台沿出口、只留上限（`topY=+∞` 的旧行为）。

### 6.5 一手描述的三问

**（a）什么情况下松手？**

1. **停止推进**：`pushIn < 0.2` 立即松脱；建议再加一个 0.10 s 的去抖（摇杆噪声不该在最高点掉下去），
   第一版可以先不加。
2. **推进方向偏离墙法线**：`pushIn = cos(偏离角)`，所以 `p_min = 0.2` ⇒ **偏离 > 78.5° 松脱**；
   60° 时 `pushIn = 0.5`，爬升速度减半。
3. **到达上限**：`h ≥ H_cap − 0.02` ⇒ 松脱、掉落。
4. **从墙顶翻上去**：球底到达顶面 ⇒ 正常退出（不掉）。
5. **墙面不再比支撑陡 15°**（面在转弯）⇒ 不算墙。

**（b）掉落时带不带离墙速度？** 建议**上限掉落带 0.3 m/s 的沿墙法线离墙速度**，松手掉落不带。

* 理由：让「墙太高」读成「被弹开、掉下来」（正合一手描述），且防止上限处悬停 / 反复起爬；0.3 m/s 只有速度上限的 7.5%，不会成弹球。
* 松手掉落不带：松手应该是「顺着墙滑下来」（`v_slide ≤ 1.0`），不是被推开。

**（c）上限之后的再爬**：一手描述只说「掉下来」。用**「掉到 `h < 0.5·H_cap` 才能再爬」**替代
「锁定到松手」：玩家一直推着墙会看到「爬—掉—再爬」。**关键补充**：重爬必须沿用
**本次贴墙段的锚点**，否则每次重爬都把上限抬一整段 `H_cap`——50°、0.6 m 台面上 D=0.30 的球就是这样
爬到 0.755 m（`H_cap` 只有 0.45）的。锚点的口径见 §6.6（它不绑定某一个面）。

### 6.6 上限是「贴墙段」的预算：锚点与选面迟滞（2026-11-17）

**问题场景**：窄 V 楔（两个竖直面、法线各偏 −Z 65°，内角 50°）里，爬升锚点按「同一个面」判定（法线点积 > 0.99、
平面距 < 2 cm、顶差 < 2 mm），不同面就把锚点重设为当前球心高度。楔里求解器逐面去掉法向分量，速度方向左右翻转，
`SelectClimbContact`（读速度方向）选作「墙」的面也随之翻转，所以每一轮「爬到上限—掉落—重爬」都换一个面、锚点上抬一截：
满推 40 s 的峰值在 D=0.30（rest 0.15 + `H_cap` 0.45 = 0.60）上是 0.69 m。若锚点随面重置，换几个朝向（偏离角平分线 3°–12°、半角 55°–72°）离线复算的球心峰值 0.81–1.15 m；锚点按「站立处」定后同一批 ≤ 0.585 m，平墙峰值 ≤ 0.58 m。楔里像烟囱一样「爬—掉—再爬」，不冻结、不进恢复（爬升让球离开起点 1 cm 圆盘，卡住计时器清零）。

**规则（一处实现：`ContactSolveMath.TryStep`，纯数学）：**

1. **锚点是「站立处」，不是「面」**。`h = 球心.y − climbAnchorY`，`H_cap` 的预算属于一段连续的贴墙过程：
   * 每个**有 RIDE 支撑、且不在爬**的子步，锚点 = 当前球心 y（站在任何东西上，那里就是新的底）；
   * 爬升开始时 `anchor = min(已有锚点, 球心 y)`（`ClimbMath.ClimbAnchorAtStart`；从未爬过/被重置则就是球心 y）。
     没有站立的球——顺墙滑下、掉过墙边——保留原锚点，所以**换面（含楔里两面、墙角转弯、被切成两段的墙）不重置预算**；
     比原锚点更低的起点（掉到旧底之下仍贴着墙）把锚点降下来，上限从最低点量起；
   * 翻上台沿（出口）后球站在台面上，锚点随即跟到台面；落回地面同理。`sameFace`（含「顶差 2 mm」）从锚点判定里删除。
2. **选面迟滞（爬升中）**。爬升存活时，求解器读的面保持为它记住的那个面（`surfaceNormal/surfacePoint`），只要该平面
   仍被接触（`ContactClassificationMath.FindClimbContactOnPlane`：同一平面的接触，取最深者）**且**对它的推入 `pushIn ≥ p_min`。
   推进转向另一个面使它的推入跌破 `p_min` 时，**同一步直接交给另一个面**（不松手、不进冷却）。平面丢失（接触消失）则回到
   `SelectClimbContact` 的常规选择。作用：爬升中的法线 / 角度 / 台沿高度 / 切线不在两面间抖动。
3. **站立门读同一个面**。电机的 `RefreshClimbGate` 改读求解器记住的爬升面（`climbSurfaceNormalWorld`），不再读「上一步按速度方向选到的墙」
   （`climbWallNormalWorld`，楔里随速度翻转，会用一个推进已转开的面松掉求解器仍有资格继续的爬升）。
   `climbWallNormalWorld` 仍保留，给「无接触悬停」时的支撑法线用。
4. **选面读速度还是读意图？** 保持读**速度**。读意图的利弊：稳定（楔里不翻），但爬升门要的是「实际在往墙里去」——
   贴墙 60°/75° 滑行时意图一直指向墙，读意图会让球反复起爬而掉速（v 1.97→0.82 m/s），读速度则一路滑过；
   且意图读法并不能保护上限（峰值是锚点问题，不是选面问题）。结论：高度上限由规则 1 担保，选面只做迟滞（规则 2），
   爬升门继续读速度方向。

**为什么不是「爬升中保持已选面直到失去接触」的字面版本**：楔里这样没问题，但墙角里（90° 内角，沿角平分线推进，
两面各 0.71）玩家转向另一面时，粘住旧面会让旧面的推入跌破 `p_min` 而松手 → 0.35 s 冷却 → 重爬，是体验倒退。
带 `pushIn ≥ p_min` 条件的迟滞在楔里同样稳定，在墙角里则无缝交接。

**测试**：`TerrainClimbTests`（纯数学，本地可跑）`AHeldPushIntoANarrowVNeverClimbsPastTheCap`（55°/65°/72° 半角 ×
7 个朝向 × 2 个偏移，每组 40 s，峰值 ≤ rest + `H_cap` + 5 mm，且上限确实被摸到）、
`AClimbThatStartsOnAnotherFaceKeepsTheAnchorOfTheStretch`、`StandingOnSomethingMovesTheAnchorToWhereTheBallStands`、
`ARememberedClimbFaceIsKeptWhileThePushStillHoldsIt`、`TheClimbAnchorIsTheLowestCentreOfTheStretch`；
`ContactClassificationTests.TheRememberedClimbFaceIsFoundByItsPlaneNotByItsIndex`；
Unity 侧（需要 GameObject，本地不可执行）`ContactModelV2Tests.AHeldFullPushIntoAFiftyDegreeWedgeNeverClimbsPastTheCap`
（真电机，0°/3°/10° 朝向满推 2000 步）。
**Unity 执行前，电机级上限不算验证**；电机级还带着卡住恢复（软恢复 `ClearClimbState` 会合法地重置锚点，因为那是一次「重新开始」），
所以若 Unity 里该测试红且 `GetRecoveryCount() > 0`，先看恢复有没有触发，再看上限。

### 6.7 墙与顶棚夹角：受阻不等于卡住（2026-11-17 拍板）

**当前决定：不做按进度释放，保持现行爬升与恢复规则。** 主人在地图 0 沙盒亲测 C25 后确认：「C25完全正常啊，谁家傻子往前推不动 不退后？」球在墙与顶棚夹角里向前推不动是受阻，不是卡住；玩家靠后退脱出，不因持续无进展而自动松脱、传送或累计恢复。

诊断上仍须区分通道与实际位移：`climbActive=True / capLock=False / actualSpeed≈0` 可以表示爬升试图抬球、顶棚推出把它压回去，不代表高度上限锁或卡死；平面 `|v|≈0` 也不能判断竖墙爬升是否有进展。电机的 `climbDiagnosticsEnabled` 默认关闭；打开后每个模拟秒输出 `[BallMotor] climb`，含 `climbActive`、`capLock`、`id`、`height`、`climbV`、`planarV`、最终接受位移的 `actualSpeed` 和 `resid`，读完关回。C25 的几何与反推诊断见 [PHYSICS_TEST_FIELD §4.9](PHYSICS_TEST_FIELD.md#49-2026-11-17-的新格c25-墙--顶棚c26--c27--c28-缓坡)。

## 7. 参数区间论证：0.222 m 球出 0.19 m 凹槽 / 上 0.30 m 台阶 / 不翻房子墙

* **出 0.19 m 凹槽**（实测，§8.3）：需要 `H_cap > 0.19` ⇒ `k_h > 0.86`。取 1.5 ⇒ `H_cap = 0.333`，
  余量 0.143（64%·D），用时 1.8 s。**这不是下界**（凹槽比 0.3 台阶容易）。
* **上 0.30 m 台阶**（E4，**可信度低**：单来源、同文自相矛盾、无逐帧素材）：若照字面取，
  需要 `H_cap > 0.32` ⇒ `k_h > 1.44`。`k_h = 1.5` ⇒ 余量 0.013（6%·D，紧）。**但这不是从原作测出来的
  下界**——`k_h = 1.5` 是我们的选择（D1），E4 只用来**检查这个选择不会与实际观感打架**；若试玩认为
  0.3 m 台阶不稳，`k_h = 1.6` 给 0.035。
* **不翻房子墙**（E8：房屋／台地高差 ≥2.5 m）：上界约束是：1.10 m 球不得翻 2.5 m 墙 ⇒
  `k_h < 2.5/1.1 = 2.27`；0.60 m 球 ⇒ `k_h < 4.2`（更松）。
  **2.20 m 包线球 H_cap = 3.3 > 2.5，会翻**——这是接受的后果：包线顶端的球本来就已经「比房子大」，
  且 `OPEN_DECISIONS`（f）说单张图实际到 2.16 m；活动边界是平面（无顶）所以永远不可爬。
* **拿不掉的张力**：E3（手册转述，**不含尺寸比例**）与 E4（低可信）都给不出 1.5。跨系列核查的结论是
  「普通墙有上限」这件事只有**方向**（E1 一手描述、E10 的 short walls、E13 的弱社区区间），
  **没有任何数值**。所以 1.5 是 **D1 的工程选择**：落在最弱的区间（1–2×）内、让参考关卡的两条实测
  几何（0.19 凹槽、约 0.30 台阶）都过得去；完成标准里的「爬墙约一个球径」随之改成「**约 1.5 球径
  （暂定）**」。参数可调，不是原作值。

**结论区间**：`k_h ∈ [1.45, 2.27)`（下界来自 E4 的字面算术，上界来自 1.10 m 球 vs 2.5 m 房墙），
试玩只取 **1.45–1.6**，推荐 **1.5**（再大是「蜘蛛球」）。**整段 PROVISIONAL。**

**RefCancer 出生槽（2026-11-16 真实数据核查）**：球出生在 (4.034, 6.781)，**距 +z 的建筑墙只有 0.09 m**
（该墙在一个三角形条带里从 −1.16 m 跨到 **+13.85 m**，`contactTopY` 就是 13.85，是这面墙的真实顶）；0.19 m

的是一面 15 m 的墙，cap+掉落是设计行为；**出生点由另一任务按数据重选**（不在本文范围）。v2 的冻结另有一条：
recovery 把「推墙」当「卡住」（每步位移 <0.5 mm 且驱动开），soft 阶段 `ClearClimbState()`、三次后进
hold——v1 用的是 `sweepStuck`，而 SweepMath 自己的契约是 blocked ≠ stuck。现行规则（`UpdateContactRecovery`）：
**受阻** = 任一接触的水平法线与**意图方向**（`ComputeDrive` 的 `intentDirection`：输入的前进/侧向轴按当前朝向合成的
有符号单位向量，不随墙面偏转的速度变化；速度方向 `contactDriveDirection` 仍只给爬升门和针尖估计用）点积 < −0.5，
受阻不计 stuck。**卡住** = 有输入、不受阻、且球心仍在本次 episode 起点周围 `ContactStuckConfineM`（1 cm）内；
不再用「单步位移 <0.5 mm」——楔里求解器逐面轮流去掉法向分量，速度左右翻转，每隔几步就有 2–3 mm 的一步，逐步阈值
会被一次次清零。角落的推导：内角 β、沿角平分线推进时法线点积 = −sin(β/2) ⇒ **β > 60° 的角落一律受阻**
（球总能靠转向/后退脱出，推挤只去掉法向分量、切向仍在）；β < 60° 的尖楔不受阻、恢复会触发：soft 1.5 s（清速度）、
hard 3 s（回最后稳定点，soft 不重新武装）、再 3 s 的第二次 hard 即第三次恢复，进 hold，所以 50° 楔从进楔起约 6.2 s
（310 步）进 hold。设计**不加**「受阻久了也算 stuck」的兜底：推墙与角落都是输入可脱出的，加了会让推墙被误判为卡住而冻结。
测试：`APushIntoATallWallIsBlockedNotStuckAndStaysControllable`（推墙 300 步 recoveries=0、不穿墙、反向 60 步离墙 ≥0.2 m）、
`ANarrowFiftyDegreeWedgeIsStuckNotBlockedAndEndsInTheRecoveryHold`（50° 窄 V 楔 330 步后 recoveries≥1 且进 hold）、
`APushIntoARightAngleCornerIsBlockedNotStuck`（90° 内角沿平分线推 400 步 recoveries=0，转身 60 步脱出 ≥0.2 m）、
`SlidingAlongAWallIsNeitherBlockedStuckNorFrozenAtAnyIncidence`（45°/75° 贴墙斜推 150 步滑出 ≥2 m、recoveries=0）。
针尖（长物件撑出的 pin）碰墙的速度响应：`TheNeedleVelocityResponseFollowsTheSolversThreeClassRules`（按类去速：CLIMB 去水平法向、RIDE 不去、NONE 去三维、深度 ≤ 0 与向外速度不动）、
`APinThatTouchesTheWallBeforeTheCoreStopsTheBallThereWithoutRebound`（针尖先于核心碰墙：球停在针尖处、不穿墙、不爬、不反弹，松手不漂、反推立刻离开）。
