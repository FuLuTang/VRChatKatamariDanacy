# 野餐草坪（PicnicLawn）目录缺口：逐档还差多少

> 状态：`MEASURED + INFERRED`，2026-11-15（**同日按 REROLL 数据挖掘修订目标值**）。**实测**部分来自 `Docs/Design/Levels/story_01_bench_size/placement.json`（127 个 props / 44 个 def）与 128 个模型的实测包围盒；**目标**部分来自 [ContentVolume](../../../Research/ContentVolume/README.md) **§4.4**（原作单关 523–3955 实例 / 107–565 种；我们按 156 种 / 650 实例规划）。§4.1 的旧目标（111/365）已作废。
> 范围：只盘点「还差多少种、还差多少件」，不改关卡 JSON、不改 Unity、不做定价。补件的生产计划见 [catalogue.csv](catalogue.csv)。

## 1. 口径

- **tier** 按物件最大边长分档，取「第一次能被吞」的球径带（与三张新图的目录同一把尺）：t0 0.02–0.099 / t1 0.10–0.139 / t2 0.14–0.199 / t3 0.20–0.299 / t4 0.30–0.449 / t5 0.45–0.649 / t6 0.65–0.999 / t7 ≥1.00 m。
- **distinct defs** = 这一档里不同的模型 id 数；**instances** = 关卡里这一档的摆放件数（同一个 def 可以放很多次）。
- 两个「缺」要分开看：**摆放缺口** = 目标 − 关卡已放（靠摆放解决）；**目录缺口** = 目标 − 目录里有（必须新做模型）。
- 目标值取 ContentVolume §4.1 的 8 档全开表；**但本关不建议跑满 8 档**（§4 给 4 档/5 档的现实口径）。

三句话读这张表：

1. **形状是「头重脚轻」**：t0 有 50 件、超过新目标（60 的一半）；t1–t7 一路缺，越往上越空。按新目标，第一关的 127 件只占 **18%**（127/690），相当于原作一个「开局段」。
2. **t1–t2 缺的是「摆放」不是「模型」**：这两档目标 12/20 种，目录里已有 26/23 个可选，**关卡只摆了 5/5 个**。把现有目录摆进去就能补 22 个 defs，不需要新模型。t3 起目录也开始不够（缺 3 种）。
3. **t3–t6 是真缺口**：目录里 19/13/10/6，目标 22/32/24/20，**还差 50 个模型**（t3 缺 3、t4 缺 19、t5 缺 14、t6 缺 14）。t4 最空：它是「球从灌木级长到家具级」的主战场（200 实例），却只有 13 种。t7 也缺 6 种（场景件，不计可吸实例）。

## 4. 本关到底该开几档

- **3 档（t0–t2，球 0.30–0.60 m）**：目标 **220 实例 / 42 种**。现状 127/44 → 实例缺 **93** 件，种数已够（44 ≥ 42），**纯摆放工作**。
- **5 档（t0–t4，球 0.30–1.00 m）**：目标 **505 / 96**。实例缺 **378** 件；t4 要先补 **19 种模型**。
- **8 档全开（球 0.30–2.20 m）**：目标 **690 / 156**，实例缺 **563** 件、净缺 13 种——这就是本文的目标口径。
- 结论不变：**先按 3 档（t0–t2）验收摆放**，t3–t6 靠生产方式逐批补模型；一次性把 650 件摆满要等模型补齐（见 §5 的生产批次）。

本文建议**先按 4 档验收**，把 t4 作为「长大后的下一关」的入口，而不是硬塞进第一关。

## 5. 本轮目录补了什么

`catalogue.csv` 共 143 行：48 个现有 + **40 个 pilot**（t0–t3）+ **55 个 planned**。

- **40 个 pilot** 全部落在 t0–t3，专门补「小件轮廓不够」：长条（牙签、树枝、草叶、吸管、筷子、餐叉、餐刀）、扁平（邮票、糖包、硬币、票根、纸垫、明信片、砧板）、圆形（纽扣、弹珠、榛子、瓶盖圈、胶带卷、盐瓶、果酱罐）、块状（骰子、橡皮、火柴盒、药盒、糖果条、玩具车、眼镜盒、订书机、肥皂、酱料瓶）。

## 7. 未验证

1. 目标值 10/12/20/22/32/24/20/16 种、30/90/100/85/200/75/110/0 实例：**种数来自目录规划，实例数来自 REROLL 数据挖掘的单关分布**（ContentVolume §4.4，`[data-mined]`）。「650 实例」是把原作 600–900 的下沿取整，不是我们实机验证过的数。
2. 127 件实际只能撑到 3 档（t0–t2），取决于运行期的吸收门槛（`absorbDiameterReq`）与球径增长曲线；本表只按「最大边 vs tier」分类，没有模拟实际能吃到哪一件。127/650 = **19%**。
3. 「650 件」在 2–3 分钟里是否吃得完，**没有实机验证**：按 10× 体积规则复利，吃 0.35 D 的件需要约 143 件才能从 0.35 长到 2.6 m；650 件是「够吃、密度接近原作」的量级，但我们的时间比原作短 3–7 倍，**可能需要分两关或加体积增益倍率**（ContentVolume §3.1）。
4. 目录里 t0 有 36 个 defs、t1 有 26，超过单关目标 10/12；这是**为多个关卡/多张图共用**而留的余量，不代表第一关要全用，也不能抵 t4–t6 的缺口。
