## 4. 引擎侧事实：这台 motor 对地形能付得起什么（与研究无关）

> 本节全部是仓库内可验证的现状，不依赖原作数据。**它只回答「能做什么」，不回答「原作是什么」。**

### 4.1 支撑查询的形状（这是最重要的约束）

- 模型是「**球心正下方选一个局部平面**」：`SupportSurfaceMath.TryResolveSupport` 在「球心 XZ 上方最高者」里选一个候选，返回 `(surfaceId, point, normal, height)`；`GroundContactMath.TrySolve` 拿这个平面对 16 方向代理点求支撑高度。**没有任何「找最近三角面」的路径。**
- 候选来源固定四类：地面平面（1 张，`SetGroundPlane`，`normal.y > 1e-3` 才收）、静态盒顶（≤8）、斜面（≤4，**只支撑、绝不进扫掠**）、道具顶面（≤6）。
- 台阶规则：`stepLimit = 0.25 × 语义直径`（`TryStepHeightLimit`），静态盒的「是台阶还是墙」由**一个掩码**给出，掩码刷新门控是「直径变化 > 2 mm / 参考高度变化 > 5 mm / 盒集合变化」。
- 下落规则：面 id 变了**且**高度差 > `supportDropTriggerM = 0.01` 才进入重力下落；同一个面连续变低不算掉走（TERRAIN_SUPPORT §4.7）。这条决定了「地形采样必须给出稳定的面 id」。
- 因此：任何「每步给一个 (h, n)」的地形表示都能**零改动**接进 `GroundContactMath`；任何「要在一堆三角形里找最近点」的表示都要新写查询、BVH/网格索引与参考模型。

### 4.2 三种表示 × 这台 motor 的可行性

| 表示 | 每步成本（估算） | 内存/序列化 | 表达力 | 判定 |
|---|---|---|---|---|
| **分层图元**（今天的 plane/box/ramp/curve 补丁） | ≈1.6k flops/步（盒子每次投影；`CONTACT_MODEL_V2` §5.5 的 v1 估算） | 极小（几十条 JSON 记录） | 平地、台阶、直坡、竖直弯坡；**表达不了沟/池塘/路拱** | **可作为回退与迁移目标**，单独用不够 |
| **高度场格（局部 patch）** | 1 次双线性 + 4 邻域梯度 ≈ 5 次采样 ≈ **20 次数组读 + ~40 flops**，占 v1 每步预算 **~1.5%** | 见 §4.3 表；格点可用 `int16 mm` 定点（与 (r) 同风格） | 任意「单值高度」地形：沟、池塘凹陷、路拱、缓坡；**表达不了悬垂/隧道/桥** | **主推候选**（如果 Q-T5 说没有悬垂） |
| **三角网格（运行时查询）** | 最近三角要空间索引（Udon 无 `List`/指针/BVH 现成件），最坏 O(n) 或自建网格 3×3 邻域；参考模型与测试要重写 | 顶点+索引数组，规模未知 | 最全（悬垂、隧道也能表达） | **只做离线烘焙源**，不做运行时查询；除非 Q-T5 明确有悬垂 |

**结论（引擎侧，非最终设计）**：主推「**局部高度场 patch**」，回退「**分层图元**」；三角网格只作为 authoring/导入侧的来源，导入时烘成前者。最终选哪种要看 Q-T1/Q-T5。

### 4.3 预算表（按 Cancer 的 bounds 估算，**未实测**）

| 1.00 m | 59×81 ≈ 4.8k | **9.6 KB** | 19 KB | 4.5 直径/格（台阶开始失真） |
| 2.00 m | 30×41 ≈ 1.2k | 2.5 KB | 4.9 KB | 9 直径/格（只能做缓起伏） |

三条由算术直接得到的结论：

1. **单一全局格距不可能同时服务 5 cm 球与 2.2 m 球。** `_ref_mas1` 起始 0.05 m 球，若格距取「≈1 个球半径」= 0.025 m，58×80 m 要 **≈740 万格 / 14.8 MB**（`int16`）——Udon 与场景序列化都装不下。所以格距必须**按 patch 定，且与该 patch 上会滚的最小球绑定**；有机起伏走粗格 + 台阶/台沿走图元，是算术上的必然，不是偏好。
2. **JSON 内联大格是文本炸弹。** 规范形是 2 空格缩进、数组逐元素换行；19k 个整数 ≈ 19k 行 / ~110 KB 文本，diff 不可读，场景 YAML 同量级。粗格（≤512 格）内联没问题；大格要么**旁挂二进制 + sha256 钉住**（同 (g) 的指纹口径），要么换表示——**决定项 D-2**。
3. **`long[]` 与 `JsonUtility` 的 `long` 都还没在 Unity 验过**（(r) 的「未验证项」原文）。地形/体积一旦依赖它们，必须先在编辑器和 Udon 里各验一次，不能只在 Python 侧成立。

### 4.4 只靠引擎就能定死的五条（研究改不了）

1. **地形不进水平扫掠。** 斜面已经是这个规矩（「坡只支撑、绝不进扫掠」），理由是坡底会出现隐形墙。地形同理：**能挡球的必须是 slab 或平面**，地形只提供可行走面。
2. **地形的面 id 必须稳定。** 采样高度每步都在变；若 id 随格变，`sameSurface` 抑制失效 ⇒ 每步都判「掉走」⇒ 球在斜坡上抖着落。所以 id 的粒度是 **patch（或 patch 内分区）**，不是格。
3. **采样要取足迹最大值，不能只取球心。** 现有支撑模型是「在 XZ 上找最高候选」；只采球心会让球陷进小丘半个球。至少 5 点（中心 + ±r 四向）取最大、法线用梯度混合。
4. **球变小/变大必须重采。** 半径变了，`r` 偏移点与 `stepLimit = 0.25·D` 同时变；掩码门控只在静态盒上有，地形侧要自己按半径变化重采（阈值 < 2 mm 可省）。
5. **地形只表达「单值高度」。** 任何悬垂/隧道/桥必须在 `structures` 里以 slab 表达；否则要么球从下面穿过时被地面顶起来，要么球从上面过时掉进空腔。这是表示的硬边界，不是实现细节。

### 4.5 现有结构怎么迁移（引擎映射已可定，语义再等研究）

| 今天 | v2 落点（**待研究确认命名**） | 为什么这样分 |
|---|---|---|
| `role=ground`（1 张无限平面） | `terrain` 的一个平面 patch；同时保留「全局兜底平面」的语义 | 它是 `SetGroundPlane` 的唯一消费者，也是没有地形时的回退 |
| `role=boundary`（≤8 张无限半空间） | 仍是平面（`AddPlane`），进 `terrain` 或 `activityArea` 的边缘 | 换成盒子会让墙顶变成可站的窄条，且吃掉盒预算（LEVEL_AUTHORING §4.3 已写明） |
| `role=ramp` / `curve_ramp` | `terrain` 的坡 patch（字段基本不变；弯坡仍展开成 N 段 slab） | 坡是可行走面，不是障碍；今天已经在 `AddRamp` 这条「只支撑」的路上 |
| `role=box` | **默认原路进 `structures` 的 OBB**（扫掠 + 顶面支撑，与今天 `AddBox` 逐位等价）；step/台沿是否改判给 `terrain` 是**作者决定 + 校验器管** | 保 v1 行为不变是转换器的第一优先（R14）；把盒子改判成地形会改语义，不能默认做 |

### 4.6 与「不做高度场」这条既有决定的关系

TERRAIN_SUPPORT §3.1 原文是「**不做高度场**」，理由是当时关卡只有「平面 / 盒顶 / 矩形斜面」三种，平面表是**精确**的。同文 §0.5 把高度场列为**逃生舱**，§0.6 给了触发条件：关卡出现**曲面或凹结构**（滑梯、碗、隧道）且数学量级超过 `SupportSurfaceMath` 的 3 倍。

所以 v2 加地形不是「顺手改」，是**推翻一条有记录的决定**。按 AGENTS.md「Original-first」与 PARITY_AUDIT 的流程，它需要：
1. 一行分歧记录（原作地形 vs 我们的平地 + 盒子；理由：原作有真实地面建模，属于「我们的设计可能错了」的信号）；
2. 一个可复算的触发依据（Q-T1/Q-T5 的答案：地形里确实有沟/池塘这类单平面表达不了的东西）；
3. owner 的 `restore` 决定。
**这三条没齐之前，不要在代码里开始加地形。** 本文 §4 只证明「加得起」，不证明「该加」。
