### 交分与回合规则（2026-11-14 拍板）

这四条原先列在本文的开放项里，现已决定。**标 PROVISIONAL 的数值是本项目自选暂定值**——原作只确认“会变小／太小不给分／约每分钟换位／结算有+50pt”，没有公布比例、门槛、精确秒数或奖励项清单，所以下列数值不得写成原作值，须在 T01 规则冻结与 T21/T39 试玩后复核。决定本身不改变任何任务依赖。

- **（a）交分时球的缩小规则 — 已选 A：按比例缩小、保留残余体积，不重置回初始体积。** 公式 `post = max(start, start + (pre - start) * residual)`，`residual = 0.25`（PROVISIONAL；`start` 为初始球径 0.30 m，野餐草坪尺度）。依据：[研究核查](Research/KatamariBallRules/README.md) C2/C5（Tier 1 制作人「変換エリアでは塊が小さくなるのと引き換えにポイントを獲得」＝在兑换区用球变小换积分；缩球后卷不动大物件）与 C20（原作用词只是「小さくなる」，未说清空回初始球，判 unconfirmed／与证据不符）；原作没有给比例或公式，公式与 0.25 都是本项目自选，用户 2026-11-14 决定。保留备选历史（均已否决）：B. 扣“本次交分体积”的固定比例并设下限；C. 维持回到初始体积（与 C20 冲突）。实现口径见 `Docs/Design/Gameplay/round_model.py` 的 `post_bank_diameter()`。
- **（b）最小兑换体积门槛 — 已选 A：绝对门槛。** 球径小于 `0.55 m` 不能交分，交分请求被拒绝、不产生分数（0.55 m 为 PROVISIONAL）。依据：原作确认“球太小不给分”（C4，Tier 2「小さい塊の場合は、ポイントをゲット出来ません」），但数值未公开。取值依据来自离线模型（[Gameplay 报告](Design/Gameplay/README.md)）：residual 0.25 下 0.55 m 的球交分后为 `0.30 + (0.55 − 0.30) × 0.25 = 0.3625 m`，比 m 档拾取门槛 0.32 m 高 4.25 cm；**安全下限 0.38 m**（须满足 `0.30 + (min − 0.30) × 0.25 ≥ 0.32`），低于它会逼近 0.32 m 中档门槛、缩球后吃不到中档物件。已否决：B. 设“本次未交存收益”门槛；C. 不设门槛、只靠交分缩小自然抑制刷分。
- **（c）兑换区轮换周期 — 已选 A：对齐原作约 60 秒。** 4 个固定台轮换，激活时刻 `0 / 60 / 120 / 180 s`；180 s 单局只有 3 个 60 s 窗口（0–60 / 60–120 / 120–180），第 4 台在终场哨才激活、本局不用；下一局轮换起点按 +1 台偏移（按房间内已完成局数推进、单局内恒定），避免任何一个台永久闲置。依据：C3（Tier 2 实机＋Tier 3 wiki 一致：「1分毎に移動」，有导航图标；属 `[原作强暗示]`，不是 Tier 1 原话）；精确秒数未确认，不得把 60 秒写成原作确认值。已否决：B. 保留 45 秒（旧项目值，已作废）；C. 按地图分别配置。具体布局见[野餐草坪 §6 交分区与轮换](Design/Maps/PicnicLawn/README.md)。
- **（d）结算奖励层 — 已选 B：采用原作奖励层，作为第二层。** 结算按 3 个项目各给第一名 +50 pt，交分（已交存积分）仍是唯一主计分通道；每局具体取哪 3 项原作未公开（实机观察出现过吞掉的球数／冲刺次数／道具使用／获得的 Brother 数／最大球尺寸）；本项目模型默认取吞对手数／最大球径／拾取件数、平局不发，清单与平局规则须在 T39 前确认并公开告知玩家。依据：C11/C12（Tier 2 玩家实机「3つの内容で其々1位になった人に 50pt付与」，「1位になっても、此処で順位が変動してしまう場合が…」＝拿了第一也可能在这里被翻盘）。已否决：A. 不启用；C. 启用但压低权重/只作展示。

### 地形门、成长包线与地图指纹（2026-11-14 拍板）

同 (a)–(d)：这三条是“按这个口径往下做”的决定，不是验证通过，也不改任务依赖。前两条须在 T06 尺度冻结与 T21 灰盒实测后复核；第三条只约束关卡数据与校验器的写法。

- **（e）12% 坡度上限只管可驶坡道，不管尺寸门台阶。** `layout.json` 的 `scale.max_traversable_slope_percent = 12.0`（PROVISIONAL）约束的是**球要滚上去的可驶坡面**；竖直台沿／平台边只要用途是**尺寸门**，就不算违规。例：花圃木框 0.26 m 台高 / 0.9 m 斜面 = **28.9%**，它的判据是“球够不够大”（`size_gates` 的 `climb` 门，门槛 1.10 m，0.95 m 的球上不去），不是“坡够不够缓”——与原作同构：能不能越过去看球的大小（[规则矩阵](Research/ReferenceRules/rules_matrix.md) 的尺寸分档 C6/C9 是尺寸判据；原作未公布坡度与台阶数值，所以 12% 与 0.05 m 都是 `[项目自选]` 暂定值，见 02 §3.2“坡道、台阶…还需实现和测试”）。**不要为了消掉这个百分比去降台面**：压到 ≤0.11 m（或把斜面拉到 ≥2.2 m）会让 0.95 m 的球直接滚进花圃，门就废了。口径后果：地图数据要逐面声明 `traversability.class`——**可驶坡 `drivable_grade`（`run_m` 必填、坡度现算，查 ≤12%）／爬升台阶 `climb_step`（`step_height_m` 必填，查“台阶高 ÷ 球径 ≤ `max_step_height_over_ball_diameter` = 0.25”）／障碍 `obstacle`**——通用校验器（`Tools/mapbuild/validate_map.py`）按类别分别判，不再用一个全局坡度阈值扫所有立面。现状（写入本决定时在工作区、尚未提交）：`layout.json` 已升到 schema 2，花圃木框声明 `climb_step`（step 0.26 m / run 0.9 m；0.26 ÷ 0.25 = 1.04 m 是最小可翻球径，与该 `climb` 门的 1.10 m 门槛相容），树根丘声明 `drivable_grade`（run 1.25 m、11.2%，由 `64e0de3` 压到上限内）。逐面分类本身是 `[项目自选]` 的工程写法，不是原作规则；原作只给“球够大才翻得过去”这个形状。
- **（f）2.20 m 是包线天花板，不是一张图里能滚到的直径。** 成长标定 `units_to_max_diameter = 1356` 价值单位 = 0.30→2.20 m 的一次满径成本（PROVISIONAL，见 [Gameplay 报告](Design/Gameplay/README.md)）；但野餐草坪活地图只有 **1284 单位**，把整张图吃光也只到 **2.16 m**。决定：**保留 1356 标定**（它是成长节奏参数，不是可达性承诺），把 2.20 m 写成**包线上限**；真要出现 2.20 m 的球，只能靠补货（T22）或加地图内容，且**现在没有任何一关需要它**——剧情两关的三星目标一关是 1.60 m、一关是 30 件（`Docs/Design/GameModes/Levels/*.json`），都不碰 2.20 m。设计文档里的包线一行统一写成“**0.30–2.20 m 包线；1284 单位的地图上实际 2.16 m**”，不要再出现“最大球 2.20 m”这种会被读成单图可达值的写法。若以后要 2.20 m 变成常规体验，动的是补货预算或地图内容，不是把 1356 改小去凑（那会同时把 t3 提前，等于换成长节奏）。
- **（g）关卡数据用 sha256 钉住地图，校验器在指纹不符时直接报错，哈希绝不手抄。** 每份关卡 JSON 带 `map_snapshot.layout_sha256` / `catalog_sha256`；`Docs/Design/GameModes/validate_levels.py` 逐字节比对实际的 `layout.json` / `prop_catalog.csv`，不一致就报“地图已变更，请复核…”，并且**不自动改写**——改完地图必须复算目标／阈值再重钉，而不是让工具顺手把哈希刷新掉。依据：手写哈希今天已经漂了三次；就在本次地图 schema 2 落地后，`Docs/Design/GameModes/README.md` §0.2 的表项与 schema 示例块里那两个手抄值又和实际文件对不上了（以 `validate_levels.py --json` 的输出为准，不要回头去 README 抄数字），[野餐草坪 README](Design/Maps/PicnicLawn/README.md) 也已写明“禁止手抄”。重钉只认工具输出：`validate_levels.py --json` 摘要里的两个哈希，或直接对文件跑 `sha256sum`；**不得从别的文档复制**。这是 `[项目自选]` 的工程约束，不是原作规则。实现状态：机制已落地，`5ee89c2` 与今天 schema 2 落地后各用工具输出重钉过一次两关；`Docs/Design/GameModes/README.md` 里的手抄残留仍待 GameModes 负责人清零。任何地图改动都会让两关快照失效、必须重钉后才算改完——今天已经真实发生过一次。

### 拾取层：吸收门槛与接触余量（2026-11-14 拍板）

同 (a)–(g)：这两条是**运行时契约**层面的决定（decided），不是测量结果，也不改任务依赖。它们钉住的是“现场调试时两个 agent 各自把 reach／门槛算错”那类问题的口径；代码改没改另说。

- **（h）可吸收性按球的尺寸相对判定，不按绝对 1 m。** ⚠️ **本条的具体形态已被 (l) 取代（2026-11-15）：判定量从「最长边」改为「AABB 体积」，`absorbSizeRatio` 与 `maxItemSizeWorldM` 两个字段已删除。** 保留原文作为历史；其中仍然有效的两条结论是「门槛是相对的、随球长大」与「pickup 尺寸 / bounds / reach 半径是三个量，不要互换」。(h) 的经过：吸收比例 `absorb_size_ratio = 1.0`（PROVISIONAL）：直径 **D** 的球吸收 pickup 尺寸 ≤ **D × 1.0** 的物件；序列化的绝对上限 `maxItemSizeWorldM` 只保留为**安全上界**，不再是玩法规则。依据：回合模型的门槛是相对的，`Docs/Design/Gameplay/round_model.py:119` 写明 `absorb_size_ratio: float = 1.0          # item pickup gate <= ball diameter * ratio`，判定在 `round_model.py:493-502`：`pickup_diameter_m <= ball_diameter_m * absorb_size_ratio + 1e-9`（边界含等号；[Gameplay README L47-50](Design/Gameplay/README.md#L47-L50) 同一说法）。今天两侧不一致：运行时 `PickupAbsorbMath.cs:134-135` 拿 `largestExtent > maxItemSizeWorldM` 直接拒收，`KatamariBallMotor.cs:113` 的 `maxItemSizeWorldM = 1f` 是序列化默认（`KatamariBallMotor.cs:653` 原样传进判定），所以**2.20 m 的球仍吃不到最大全长 1.2 m 的道具**（1.2 > 1 拒），而模型给 `1.2 ≤ 2.2 × 1.0` 放行。口径后果：运行时必须**每步用当前语义直径（与碰撞半径同源）算上限**，不能再用固定 1 m；`maxItemSizeWorldM` 退化为上界时仍要显式写出来，别让它悄悄变成第二个玩法阈值。**两个量不要互换**：模型比的是 `pickup_diameter_m`（地图档位/道具声明的 pickup 尺寸，`round_model.py:174`、`:243`），运行时比的是 `bounds` 的最大全长（`PickupAbsorbMath.cs:134`）——把 AABB 全长当 `pickup_diameter` 等值代入，是同一类算错。PvP 那个 1.35 不是本条的吸收比例，别混用：`round_model.py:141` `swallow_diameter_ratio: float = 1.35    # - **（i）`contactRadiusWorldM` 保持 0，且这 0 是项目决定，不是占位。** reach 的容差已经全部由包围球代理提供（`PickupAbsorbMath.cs:155-157`：`reach = collisionRadius + contactRadius + itemRadius`，`itemRadius` 为包围球半径 √((x/2)²+(y/2)²+(z/2)²)），所以 0 的语义就是“球必须实质接触物件、没有额外手感窗口”，不是“这个功能还没接”。工作面算例（球在起始直径 0.30 m、碰撞半径 0.14987 m、`contactRadiusWorldM = 0`、物件为边长 s 的立方体，`bounds = (s,s,s)`）见下表。

| s (m) | itemRadius = √3·s/2 | reach（contact = 0，今天的行为） | 面心真接触距离 = 球半径 + s/2 | 包围球多放行 |
|---:|---:|---:|---:|---:|
| 0.10 | 0.0866 | **0.236** | 0.200 | 0.037 |
| 0.25 | 0.2165 | **0.366** | 0.275 | 0.092 |
| 0.35 | 0.3031 | **0.453** | 0.325 | 0.128 |
| 0.50 | 0.4330 | **0.583** | 0.400 | 0.183 |

读法：多放行的量是 `(√3−1)/2·s ≈ 0.366·s`，**只跟物件边长有关、与球径无关**；所以“看着还差一点就已经吸到”是包围球代理的正常行为，反过来“视觉上贴住了却不吸”才是 reach 算错（位置快照过期，或宿主把 `bounds` 填得比画面小），不是场景要调。完整推导见 [PickupAbsorb README 第 1、2 节](Design/PickupAbsorb/README.md#L77-L115)，同一张表的展开版在其 L88-93。

**（i）取代的旧说法：** `Design/PickupAbsorb/README.md` L77／L79／L222 与 `Design/BallMotor/README.md` L188 把 `maxItemSizeWorldM`／`contactRadiusWorldM` 一并称作“占位”的定性——`contactRadiusWorldM = 0` 自此是有意的项目决定，绝对上限的地位改由 (h) 定义；那三处措辞等各自 owner 下次触碰时改一句，本次没有动那两个文件。

- **（j）账本 gain 是整数单位，这是有意的；小数道具价值是作者数据错误，以 `RejectNoGain` 大声拒绝，不静默截断、不四舍五入。** 代码路径只有一条：宿主提交候选时把 `valueUnits` 原样存进候选槽（`KatamariBallMotor.cs:1013`），判定时 `EvaluateAbsorbWithValue` 先过几何门、再用 `TryAbsorbValueToLedgerGain` 换 gain，换不出来就返回 `RejectNoGain`（`PickupAbsorbMath.cs:254`），换出来但 gain ≤ 0（即价值为 0）同样拒绝（`:255`），拒绝随即进电机拒绝环（`KatamariBallMotor.cs:711`）；换算本体先截断成 `int truncated = (int)itemValue`（`PickupAbsorbMath.cs:266`），再要求 `(float)truncated == itemValue` 逐位相等，不相等即 `false`（`:268`），负数、非有限值与 ≥2³¹ 的值同样先拒（`:262`、`:265`）。理由不是“整数好实现”：确认体积在账本里与 `banked_score`、每个事件 gain 共用同一个整数单位（`GrowthLedgerMath.cs:52-54`），账本只接受确定性权威提交（[Ledger README L7](Design/Ledger/README.md#L7)），而整套成长标定本身就是按整数单位写的——0 单位对应 0.29974 m 的起始语义直径（[BallMotor README L130](Design/BallMotor/README.md#L130)），1356 单位对应 2.20 m 满径（[Gameplay README L56](Design/Gameplay/README.md#L56)）。小数价值落在两个整数之间，在成长曲线上没有对应分数，也就没有一个可以被两台客户端都算成同一个数的总分。**对内容的后果：** 每件道具的 `valueUnits` 必须是 ≥ 1 的整数——填 0 或 0.5 让这件道具**永远不可吸收**，跟球贴得多准、reach 算得多对无关；实验室宿主把 `valueUnits` 暴露成一个可序列化 float（`PlaygroundProp.cs:45`），所以这种值在编辑器里没有任何阻拦，只会在运行时以 `noGain` 暴露。**调试教训（这条错花了三轮）：** 拒绝在外部只表现为 `noGain`，与“球根本没碰到道具”在读数上无法区分；必须打印**那件道具**被电机收到的价值（`pv`，`CpuSkirmishBootstrap.cs:208`，读的是候选槽里的原值 `KatamariBallMotor.cs:1645-1649`），而不是电机级“最后一次拒绝”的聚合（`CpuSkirmishBootstrap.cs:168-175` 的 `rej=`）——聚合会把上一件道具的拒绝盖到当前目标上，于是“道具自己写的 1.0125 旁边挂着 noGain”被读成了几何或接线问题（那批实验室道具的价值是按 `s³ × 300` 手算填的：边长 0.15 m → 1.0125、0.2 m → 2.4、0.25 m → 4.6875，逐个都过不了整数门）。**这不是以后要“修”的 bug：** 改成静默截断或四舍五入会把作者错误藏起来（道具看起来被吃了、分数却没动），并让两台客户端对同一份提交得出不同的总分；该放松的是数据（把价值表改成整数），不是这段判定。

### 跟随架眼点：球后上方、随半径线性（2026-11-15 拍板）

同 (a)–(j)：这条也是“按这个口径往下做”的决定，不是测量结果，也不改任务依赖。它定的是**玩家视点**（跟随架参考帧）的几何；Unity 侧已是该实现，Python 孪生与两侧测试同日追平。

- **（k）眼点 = 球心后方 + 上方，两项都随球半径线性放大，不再有「离球心常量眼高」。** 公式 `eye = ballCentre − forward(滤波后的 yaw) · (eyeBaseBackMeters + radius · eyeBackPerRadius) + up · (eyeBaseUpMeters + radius · eyeUpPerRadius)`，默认 `0.75 + 2.2r` 后退、`0.55 + 2.4r` 抬高，护栏 `eyeUpMinMeters = 0.1` / `eyeUpMaxMeters = 8`（钳**离球心**高度）、`eyeMaxBackM = 8`（钳后退）。四档直径（0.10 / 0.30 / 0.72 / 1.43 m）算出来是：上方 0.670 / 0.910 / 1.414 / 2.266 m，后退 0.860 / 1.080 / 1.542 / 2.323 m，球面净空（上方 − 半径）0.62 / 0.76 / 1.05 / 1.55 m。依据：旧语义 `y = 球心 + 1.6` 的净空是 `1.6 − r`，0.30 m 球 1.45 m、1.43 m 球 0.885 m；而吸附物站在球面上、约一个物件深（吸收门槛是「物件最大边 ≤ 球半径」），球越大画面越被糊满——1.43 m 正是设计判定的最坏档。改成随半径增长后净空**变大**，平视时「球 + 吸附壳」上沿仍在视轴下 20.4°–32.7°，球留在画面下缘而不是糊住中间。已否决：A. 保留常量眼高（净空线性下滑，1.43 m 时只剩 0.885 m）；B. 只抬高不后退（球顶在视点正下方，吸收物直接糊镜头，也失去“推球”的纵深）；C. 改成按「离球顶」定义高度（等于把半径从式子里再减一次，净空还是常量，换名字不换问题）。数值全部 PROVISIONAL，须在 T05/T06 的舒适性与尺度门禁里由真人头显复核；公式本身是几何，不是舒适参数。
- **（k）的硬约束：`VRCStation` 是这台引擎上唯一能连续移动玩家的手段。** VRChat **没有**任何 API 能连续移动玩家 avatar，可用的只有 `VRCStation` 与传送。所以「人推球」只能实现成**摆在球后方的一个 station**：第一人称下玩家看到的正是「球在身前、视角在球后上方」，与推球一致；第三人称会看到 avatar 是坐姿——这是引擎限制，不是设计取舍。这条同时解释了为什么方案不是「让玩家自己走、摄像机跟球」：玩家自己走既不能保证与球同速同向，VRChat 里也没有“每帧把玩家搬到某点”的接口。口径后果：motor 只写 `followRigRoot` 的 position + yaw（不碰 HMD、不写玩家位置），Station 挂在这个根下，且它的局部偏移**不能**再叠一层「球后上方」——旧文档的 0.25–0.5 m 眼高 + `(0, 0.8, −2.2)` 偏移在新语义下会叠成约 4 m 后退，已作废。代码位置：`FollowRigMath.TryUpdate`（`Runtime/BallLayers/FollowRig/FollowRigMath.cs`）、7 个字段 `KatamariBallMotor.cs:137-143`、`UpdateFollowRig` 与 `ApplyPresentation`（`:1004-1032`）。
- **实现状态（2026-11-15）**：C# 已是该语义；Python 孪生 `Docs/Design/BallLayers/FollowRig/follow_rig.py` 的 `try_update(...)` 与 C# `TryUpdate` 同名同序（含调用方持有的上一帧位置/yaw/离球心高度），`Docs/tests/ball_follow_rig/` 由 8 例改为 9 例（新增四档直径的球后上方检查，期望值手算），`Docs/tests/ball_visual_roll/test_presentation_cross_layer_simulation.py` 的 4 处旧调用一并改完；`Docs/Design/BallMotor/README.md` 的「跟随架」表、`Docs/Design/BallLayers/FollowRig/` 的三份文档与 `Docs/Design/Parameters/README.md` 的重复清单已同步。**未在 Unity、UdonSharp 或 VR 中运行**，第三人称坐姿与坐姿视点补偿仍待 Build & Test。

### 吸收尺寸门改为体积口径（2026-11-15 拍板）

同 (a)–(k)：这是**运行时契约**层面的决定（decided），不是测量结果，也不改任务依赖。与 (h) 的区别不是参数，而是**判定量换了**：从「物件最长边 ≤ 球直径 × 比例」换成「物件体积 ≤ 球体积 ÷ 比例」。

- **（l）吸收判定用体积，不用最长边：`a·b·c ≤ (π/6)·D³/10 ≈ 0.05236·D³`。** 其中 `D` 是球的**语义直径**（不是碰撞半径），`a·b·c` 是物件 `bounds` 的三轴乘积（AABB 体积），`10` 是 `absorbVolumeRatio`——球体积必须是物件体积的 **10 倍**。等价写法是 `D ≥ 2.154 × d_eq`，`d_eq = (6·a·b·c/π)^(1/3)` 是物件的体积等效直径；对**立方体**它化简成 `D ≥ 2.673·边长`（因为立方体的 `d_eq = 1.2407·边长`）。依据：[ABSORB_SIZE_RATIO.md](Research/KatamariBallRules/ABSORB_SIZE_RATIO.md)（14 条来源、逐条分级）。**证据等级：中**——一份社区数据挖掘直接陈述 10× 体积判定与「Size to roll up = 能滚起它的最小球径」（S-AR01/S-AR02）；9 个物件按门槛反算体积，8 个落在 ±25% 内（S-AR05 等）；三处旁证同向（Fandom「包围盒含空腔」与「铅笔比橡皮好吸」S-AR07、游戏内铅笔 4.3 cm < 橡皮 8.1 cm、玩家观测帖 S-AR12）。**常数 10 本身只有一份独立来源**：若真值是 8 或 12，所有门槛按 `(c/10)^(1/3)` 缩放，即 −7%～+6% 的球径，量级上不改变口径结论。现状审计（改前）：[SIZE_GATE_AUDIT.md](Design/PickupAbsorb/SIZE_GATE_AUDIT.md)。
- **为什么必须换量而不是调系数（用户给的具体例子，留档）：** 测试场景里黄色小方块边长 **0.05 m**、红色方块 **0.30 m**。**边长只差 6 倍，体积差 `(0.30/0.05)³ = 216` 倍。** 球能吃多少是**体积**账（球体积 ÷ 10），线性口径只拿「最长边 vs 球直径」比长短，它只能说出那个「6」，说不出 216 倍，也就无法回答「这个球够不够大」。换成系数语言：等效线性系数 `k = 可吸物件最长边 / 所需球径` **不是常数**（研究文档 §4：立方体 0.37、3:1 砖 0.78、5:1 扫帚级 1.09、10:1 铅笔级 1.74），所以任何一个 `absorbSizeRatio` 都只能在一个形状比上对——口径错，调系数只是在两个方向的误差之间挪。真实道具建模后这种差别只会更大：方糖 1.6 cm vs 野餐桌 150 cm，边长差约 94 倍，体积差约 `8×10⁵` 倍。口径的直接收益是**细长物件自动能吸**（棒球棒 0.02×0.02×0.85 m 体积 0.00034 m³，0.50 m 的球就吸得动；线性口径要 0.85 m 的球），代价是**薄片几乎白送**——两者都是原作的形状（S-AR07），不是我们新引入的偏差。
- **旧的两个线性字段已删除，不是保留兼容。** `absorbSizeRatio`（物件最长边 / 球直径 = 1.0）与 `maxItemSizeWorldM`（8 m **长度**上界）都消失，替换为 `absorbVolumeRatio = 10` 与 `maxItemVolumeWorldM3 = 512`（= 8³ m³，即「8 m 立方体」的读法：保留旧上界的量级、换成体积口径）。理由有两条：(1) 长度上界配体积门会在 8 m 处**硬截断**，语义错——一条 0.02 m 见方、8 m 长的杆体积只有 0.0032 m³，却被「8 m」这一条钉死；(2) 保留旧字段当兼容等于留一条**能悄悄把闸门压回线性**的配置路径，而这正是 (h) 已经踩过一次的坑（场景里残留覆盖值让决定不生效）。**迁移代价**：现存 lab 场景/prefab 里的 `maxItemSizeWorldM: 8` / `absorbSizeRatio: 1` 变成被 Unity 忽略的死键，组件回落到新字段的 C# 默认值（512 / 10），所以**行为不需要改场景就已正确**；清理死键属于 Unity 侧的顺手活，见下。
- **绝对上限也是体积口径，且它是护栏不是玩法。** 满径 2.20 m 球的体积 `(π/6)·2.20³ = 5.575 m³`，距 512 m³ 有 92 倍余量；`maxItemVolumeWorldM3` 只在比例被配错到很低时才会咬人。**不要**拿它当「一关里最大能吸的东西」用——那是体积门的活。
- **两件事不要混：判定量是 AABB 三轴乘积，reach 用的是包围球半径。** `TryComputeReach` 的 `itemRadius = √((x/2)²+(y/2)²+(z/2)²)` 只决定「够不够近」，与体积门没有关系；同一个 `bounds` 喂给两者。细长物件正是两者分离的典型：棒球棒的 AABB 体积 0.00034 m³，而它的包围球半径 0.425 m（reach 比体积门「宽」得多）。把最长边、对角线、包围球半径中的任何一个当体积用，都是本条点名的算错。
- **球类道具会被 AABB 算虚大 `6/π ≈ 1.91` 倍，这是忠实还原，不是 bug。** 球/椭球（种子、珠子、毛絮团、水果）的 AABB 体积比真实体积大 1.91 倍，于是需要约 `1.91^(1/3) = 1.24` 倍大的球才吸得动。原作本身也用包围盒、并把空腔算进去（S-AR07），所以这是同构而不是缺陷；要按「看起来的体积」校准，正确的口子是给每件道具存 `volume_m3`（研究文档 §6 推荐项 1 的后半句），不是把这一层改回长度。
- **实现状态（2026-11-15，C# 已落地，已编译进 Udon 程序资产，EditMode 455 条 454 过）。** 判定链只有一条：`PickupAbsorbMath.TryComputeItemVolume(bounds)`（**唯一**的体积推导，三轴乘积，溢出为非法输入）→ `IsVolumeBeyondLimit(itemVolume, limitVolume)`（**唯一**的比较，含等号在可吸一侧）→ 吸收门用它、挡路谓词 `IsBeyondAbsorbVolumeLimit(bounds, limitVolume)` 也用它，所以「太大」在运行时只有一份定义。上限合成 `TryComputeAbsorbVolumeLimit(semanticDiameter, absorbVolumeRatio, maxItemVolumeWorldM3)` = `min(ceiling, (π/6)·D³ / ratio)`；相对入口仍是 `EvaluateAbsorbWithBallSize` / `EvaluateAbsorbWithValueAndBallSize`；装配层每步重算，诊断读数改名 `GetAbsorbVolumeLimitWorldM3()`。序列化字段在 `KatamariBallMotor.cs`（`maxItemVolumeWorldM3 = 512f`、`absorbVolumeRatio = 10f`），人工仍以 `[SerializeField]` 暴露、默认值即契约。测试：`Tests/EditMode/Pickup/AbsorbSizeGateTests.cs`（含 0.05/0.30 的 216 倍与棒球棒两条新用例）、`PickupAbsorbTests.cs`、`BlockingPropMathTests.cs`、`Tests/EditMode/BallMotor/AbsorbSizeLimitTests.cs`（装配层默认值与上限读数）、`RejectNoGainTests.cs`。**Unity 侧已完成**：重编译与 Udon 程序重生成、`run_tests`（EditMode 全量 **455 条：454 过，1 红**；红的是 VRChat SDK 包内自带的网络 URL 测试，与本项目无关；`AbsorbSizeGateTests` 8/8 全过）。**仍待做**：7 处场景序列化覆盖的死键清理——那是编辑器产物，本轮不碰。**未验证：任何运行时表现**（Play Mode/VR 尚未跑）。
- **本轮有意没改、但会被本条改变语义的地方（内容侧，等真实道具落地再动）：** `Tools/mapbuild/validate_map.py` 的 `item_tier_pickup_diameter_m` 档位窗口、`Editor/Pickup/PickupFieldAuthoringRules.cs` 的 `SmallTierMaxExtentM = 0.21` / `MediumTierMaxExtentM = 0.76` 分档与 `@size=` 声明尺寸——全是**长度**口径（档位是内容侧的分档，不是运行时门槛）。改了体积门却不改它们，不会报错，只会让「档位」与「某球径下能不能吸」脱钩；**这是本条落地后第一个要复核的地方**，不是本条的缺陷。
- **已经读到的内容侧后果（2026-11-15，序列化数据实测，不是推断）**：`StoryLevel.unity` 的 `propBounds` 是按目录**最长边填成立方体**的（`0.9,0.9,0.9`、`0.52³`、`0.38³`、`0.24³`…）。体积口径下 `0.9³ = 0.729 m³` 需要 `D ≥ (6·0.729·10/π)^(1/3) = 2.40 m` 的球——超过 2.20 m 包线，**暖壶从此永远吸不到**；同一张表里 `0.52³` 要 1.39 m、`0.38³` 要 1.02 m。旧线性口径下「0.9 m 的立方体」和「0.9 m 的长条」难度完全相同，所以这个数据问题被口径掩盖了。同理 `@size=1.25` 的长凳记成 1.25³ = 1.95 m³ 也不可达。**结论：体积门落地后的第一件事是让 `bounds` 说真话——用真实渲染器 AABB 或每件道具的 `volume_m3`，不是回头调 ratio。** 这也是「球类道具虚大 6/π」那条的同源问题，只是立方体近似比 6/π 更狠。
- **离线参考模型仍是线性口径，这是已知分歧不是遗漏。** `Docs/Design/Gameplay/round_model.py`（`pickup_diameter_m <= ball_diameter_m * absorb_size_ratio`）与 `Docs/Design/PickupAbsorb/pickup_absorb.py`（`max(item.bounds) > max_item_size_world_m`）都还是旧口径；两者都是 DRAFT/离线模型、不是运行时契约，追平它们要连带改 `Docs/tests/`，本轮写范围不含，已记在 [PickupAbsorb README「与 `pickup_absorb.py` 的已知分歧」](Design/PickupAbsorb/README.md)。
