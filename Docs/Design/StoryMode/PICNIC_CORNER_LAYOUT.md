## 1. 口径（先钉住，否则下面每个数都会被误读）

### 1.1 三个判据，各只有一处定义

| 判据 | 式子 | 谁实现 | 在本布局里的用法 |

**球径上限**：`maxCoreRadiusWorldM = 1.1` → `D_cap = 2.20`。**起手**：0.29974 m（`baselineVolumeUnits 3.439` / `c = 0.0041`）。

**单位 → 球径**：`total = 3.439 + confirmed`，`V = total·0.0041`，`D = (6V/π)^(1/3)`。反解：吃一件体积 V 的东西之前，必须有 `U ≥ V/0.00041 − 3.439` 单位（下表的「门槛 u」）。

### 1.2 一条新推导：**「可爬又可口」只可能是宽扁件**

把台阶门槛和吸收门放在一起：

```
要能踩上去：rise = h ≤ 0.25·D      ⇒  D ≥ 4h
要还没被吃掉：D < D_req = 2.673·(A·h)^(1/3)
两者同时成立：4h < 2.673·(A·h)^(1/3)  ⇒  A > 3.35·h²
```

- 方盒（`A = s²`）要当成台阶，需要 `s > 1.83·h`：**0.6×0.4×0.4 的收纳箱（s/h = 1.5）不合格**，{0.4, 0.3, 0.28} 的啤酒箱（1.43）、{0.4,0.35,0.32} 的折叠凳（1.25）更不合格。
- 板/托盘（h = 2.5–4 cm）随便过：`A = 0.55×0.35` 对 4 cm 的托盘是 19 倍余量。
- **躺椅是唯一「又宽又矮又能吃」的中大件**（1.6×0.6 的足迹、0.35 高）：`A/h² = 7.8`，窗口 `D ∈ [1.40, 1.86)`，是本关唯一「踩上去之后再吃掉」的高光。

这条推导不是巧合，它解释了为什么原作的结构语言是「**板 > 箱 > 凳 > 桌**」（`LEVEL_CONSTRUCTION` R8）：**只有板能当路。** 于是本关的竖向必须由「板（斜的/平的）+ 台面（不可吸的壳）」承担，箱子只负责「挡 → 吃」。

### 1.3 P1 / P2 / P3 的含义（本文只做设计，不实现）

**读法四条**

1. **窗口右端 = `D_req`**，不是随手写的：一件东西被吃掉的同一刻，它的地形身份也消失。窗口为空（`—`）就是「爬不上，只能挡着或吃掉」。
2. **变食物之前爬不上去的 7 件**（凳 0.95、收纳箱 1.14、收纳箱 1.22、大冷藏箱 1.34、大收纳箱 1.51、长凳 1.63、婴儿车 2.19）**不是设计失误**，是 §1.2 那条推导的必然结果。它们的存在意义是「挡」与「吃」，不是「上」。
3. **「台顶→收纳箱 0.40」窗口只有 1.04–1.22**：要站在 0.26 台面上（P1 需要 1.04），跨上 0.40 要 `rise 0.14 ≤ 0.25D` 即 `D ≥ 0.56`；而 1.224 它就被吃了。**这是一条「熟练玩家的窄门」，不是主路线。**

### 4.4 斜板（2 块，P3 才有；不可吸）

| id | 定义 | 底 → 顶（真坐标） | 宽 | 坡长 | 水平 | 角度 | 只支撑 | 可吸 |

**为什么斜板必须不可吸**：`TERRAIN_SUPPORT` §6.5 已经算过——倾斜道具只知道它的 AABB，**AABB 抹掉了朝向**，所以一件「斜着的木板」在支撑表里只是一块 `1.40×0.55` 的水平搁板（`D_req` 1.73，在 2.20 之前一直挡路）。要它当坡，就必须由 `LevelArenaHost.rampBoxes` 声明成**静态斜面**，而静态斜面**永远不可吸**（`TERRAIN_SUPPORT` 11-U4-A 的取舍）。

**代价与补偿**：本关因此有 2 件「看得见、吃不到」的木板。补偿是同一款木板还有 2 件**可吸的**（`struct_plank_01` 在草坪上、`struct_plank_02` 在台面上），玩家读到的是「**有的板钉住了、有的板能卷走**」，而不是「木板是假的」。

**两条斜板的几何约束**（给实现者）：
1. **不能同时注册成盒**（`TERRAIN_SUPPORT` §5.5）：坡底会出现一堵位置完全不合逻辑的隐形墙。`LevelArenaHost` 的 `rampBoxes` 与 `staticBoxes` 必须分开填，`Setup` 的自检要挡住重复引用。
2. **顶边与台面齐平**：`ramp_to_table` 顶边 `y = 0.70` 正好等于桌面；`ramp_to_bed` 顶边 `y = 0.26` 正好等于台顶。两端 `δ = 0`，没有跨级。
3. **底边不穿地**（`y = 0` 与地面齐平），避免坡底「先下沉再爬」的隐形坎。
4. 坡度 30.0° / 10.7°，都远低于 45° 护栏；30° 是按「板长 1.40 m 爬到 0.70」反解的（`asin(0.7/1.4) = 30°`），**不是先定角度再找板**。

### 4.6 静态地形预算：8 盒 / 8 平面 / 4 斜面（**超了不是「小一点」，是 latch**）

球主控的静态地形容量是**硬的**：`AddBox` / `AddPlane` / `AddRamp` 超过槽位会**丢弃并 latch `overflowCount`**，而这个 latch **只有 `Start` 能清**——所以「先全注册、超了再说」会得到一个**永久带病的会话**，后面所有格的判据都不可信（[`PHYSICS_TEST_FIELD`](../BallMotor/PHYSICS_TEST_FIELD.md) §3.2；[`LEVEL_AUTHORING`](../Tools/LEVEL_AUTHORING.md) §4.5 的 `budget` 字段、§8 第 9 条）。

| 资源 | 上限 | 本布局用量 | 余量 | 明细 |
|---|---:|---:|---:|---|
| **地面** `ground` | **恰好 1** | **1** | 0 | 草地 `SetGroundPlane((0,1,0), 0)` |
| **平面** `planes` | **8** | **4** | 4 | 西/南/东/北 4 条无限半空间（**墙用平面不用盒**） |
| **静态盒** `boxes` | **8** | **4** | 4 | `flower_bed`（花圃台 4.0×0.26×4.9）、`shell_tree_trunk`、`shell_tree_mound`、`shell_signpost` |
| **斜面** `ramps` | **4** | **2** | 2 | `ramp_to_table`（30°）、`ramp_to_bed`（10.7°） |
| **道具支撑** `propSupports` | **6** | **峰值 3** | 3 | P2 才有；台顶/桌面/台面南沿三处采样，按最近 6 件选 |
| **挡路盒** `blocking` | **6** | **峰值 4** | 2 | 动态，见 §4.5 |
| **每步接触** `contacts` | 4 | — | — | `ContactCapacity`，不可配，不是作者预算 |

**结论：全部在预算内，余量 4 盒 / 4 平面 / 2 斜面。** arena 只注册 **1 张地面 + 4 条边界平面 + 4 个静态盒（花圃台 + 3 个地标）+ 2 块斜板**；**17 件可吸家具与 110 件小道具都是「道具」**，走 `propBounds` → 挡路/支撑的两套动态槽位（各 6），**不占静态盒**。这正是「场景用可吸物搭出来」在容量上的好处：**可吸物不进静态预算**。

**三条超预算时的处理顺序**（按性价比，不许扩容）：
1. **先看能不能用平面**：墙/边界永远是平面（1 个平面 vs 1 个盒，且平面不占支撑槽）。
2. **再看能不能并进既有盒**：例如把「指示牌」并入花圃台的外包盒（省 1 盒，代价是牌脚多出 0.4 m 的实心区），或把树根丘并进「角树 + 地面」（树根丘只是 0.14 的台阶，`D ≥ 0.56` 才用得上，必要时可以整件删掉）。
3. **最后才是「改成道具」**：让那件东西变成可吸件（`D_req` 落在 0.30–2.20 之间），它就从静态预算里消失、进动态的 6+6。**反例**：野餐桌（2.49）、公园长椅（2.47）、3.6 m 长凳（3.12）都**不能**改成道具——它们永远吸不动，改成道具就是「永久挡路的死件」，只能留在 arena 外当布景。

**给以后的静态布景的红线**：任何新增的台面/墙/斜板，**先在上表找余量**，别指望扩容；一次超容量 = 整局 session 的溢出计数被 latch，之后连「球在哪」都不可信。

### 5.3 120 s 能长到多大（算式 + 三个模型）

**先算清楚「1356 u」是怎么来的**（`c = 0.0041`）：

```
V(2.20) = π/6 × 2.20³ = 5.5755 m³
total   = 5.5755 / 0.0041 = 1359.9 u
confirmed = 1359.9 − 3.439 = 1356.4 u      ← 研究给的 1356 就是这个数
```

本方案给 **1500 u**（110 件 412 + 结构件 1088），所以：

```
全吃光的球径 = (6 × (1500+3.439) × 0.0041 / π)^(1/3) = 2.2749 m  → 被 2.20 夹住
2.20 落在 1356.4 / 1500 = 90.4% 处
```

**为什么不是「加件数」而是「加单位」**：`3.08 u/s` 是**旧内容的实测吞吐**（370 u / 120 s），它等于 `4 u/件 × 0.855 件/s`。要让 120 s 买到 1356 u，只能是 **u/件 从 3.75 涨到 ~13.6**（件/秒不变），或者多吃 3.5 倍的件（不可能：110 件全吃要 132 s）。**所以「结构型大件承担大部分单位」不是偏好，是唯一可行的杠杆**。

**三个到达成本假设下的 120 s**（价值优先 + 门槛合法，即每步挑「当前能吃、单位最高」的一件；小件 1.2 s/件 = §7.4 实测 0.855 件/s 的倒数）：

```
① 结构件 3.0 s/件（熟练、按簇链起来）      120 s → 1372 u → D = 2.200  m（74 件）
② 结构件 5.0 s/件（首次跑、要绕路）        120 s → 1244 u → D = 2.138  m（49 件）
③ 全部 1.2 s/件（= 实测均匀速率的极限）     120 s → 1472 u → D = 2.200  m（99 件）
```

**结论：上限可达，但 2.00 m 之后还有约 40 s 的「清场尾巴」**——折叠桌在 `t ≈ 81 s` 就被吃掉（1021 u），剩下的 335 u 由 4 u 的小件一点点补到 2.20。三个模型的逐段时刻：

### 7.2 到 `placement.json` 的映射（**别把可吸家具填进 `structures[]`**）

另一位设计者正在定的 `placement.json` 里，`structures[]` 是**非可吸的壳**（`role: ground/boundary/box/ramp`，占静态预算），`props[]` 是**可吸件**。本文的 `structures[]` 用的是「结构型可吸物」语义，**不能整表搬过去**：

| 本文的数组 | 件数 | 进 `placement.json` 的哪里 | 占据哪份预算 |
|---|---:|---|---|
| `props[]`（106） + `gate[]`（4） | 110 | `props[]` | 动态 6+6（挡路/支撑） |
| `structures[]` 里的 **17 件家具** | 17 | **`props[]`**（`absorbable: true`） | 动态 6+6（**不占静态盒**） |
| `structures[]` 里的 **2 块斜板** | 2 | `structures[]`（`role: ramp`） | 斜面 2/4 |
| `shell`：地面 / 4 边界 / 花圃台 / 角树 / 树根丘 / 指示牌 | 7 | `structures[]`（`role: ground/boundary/box`） | 地面 1/1、平面 4/8、盒 4/8 |
| `budget` | — | `level.budget` | 上限 `{planes:8, boxes:8, ramps:4, propSupports:6, blocking:6}` |

**两种 `expected` 口径**：只算小道具 → `propCount 110 / valueUnits 412`；算上 17 件可吸家具 → **127 件 / 1500 u**。本文把两份表分开写，就是为了让两种口径都能对上；**但静态盒永远是 4，不会因为结构件多而涨**。
