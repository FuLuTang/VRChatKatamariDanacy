## 0. 十行摘要

1. **骨架和绑定姿势在 ELF 的"动画块"里，蒙皮在"任务包内嵌的物件模型"里**——两者不同文件，缺一不可。
   我们已有这两个文件（`animationBlock.bin` + `1879b0`/`17f590` 那批），所以**不需要再取新数据**〔实测〕。
2. **Cancer 的 19 个动画类型 = 87 条剪辑、91 个蒙皮调色板槽、2–12 根骨骼**；153 个实例全部落在这些类型上〔实测〕。
3. **每类型 4–6 条剪辑**；全库 249 个动画类型、2,354 条剪辑；剪辑的**曲线组是跨类型共享的**（同一条曲线组被 69 个类型引用），
   **播放速率逐类型、逐剪辑不同**（同一个曲线组可以被 1.0× 或 1.5× 播）〔实测〕——这一点对"手感"很关键。
4. **速率现在知道了**：fps = (存的速度档 u16 ÷ 256) × 30；段长在**全库 2,354 条剪辑里恒为 1.0**；
   所以一条 30 段、速度 1.0 的剪辑 = **0.967 s** 循环一次。`ORIGINAL_MOTION_PROGRAM` 的 M5 只剩"何时切 IDLE/MOVING"未定〔实测+推断〕。
5. **螃蟹是"刚性部件骨架"，不是平滑蒙皮**：Small Fiddler Crab / Fiddler Crab / Coconut Crab 各有 5 根骨、5 个部件，
   每个部件刚性跟一根骨，调色板槽里 0 个影响〔实测〕。Cancer 的 91 个槽里 **83 个零影响、6 个单关节、2 个双关节**（都在 Lalala 一件上）。
6. **每顶点有一个 8 位"矩阵调色板槽号"**，存在顶点位置的 W 分量里（`(W>>2)&0xFF`）——参考实现用它选骨骼矩阵，
   我们的 `stage.py` 已经在读同一个值〔实测〕。
7. **`playAnimNo` 不是 PS2 实例记录里的字段**：参考实现完全不读它，它只在 REROLL dump 里；
   PS2 的 0x40 字节记录里唯一候选字节（`+0x08`）524 条全为 0〔实测〕。它的语义本文给了两种读法与证据，仍未定。
8. **Unity 侧现在没有 glTF 导入能力**：`Packages/manifest.json` 里没有 glTFast（也没有 UnityGLTF）〔实测〕。
   项目已有的 Blender 管线（FBX 导出、GLB 导入）可以走 "GLB → Blender → FBX → Unity"，不必给世界加运行时包。
9. **地图编辑器已经能直接吃带 skin + animation 的 GLB**：`Tools/leveleditor/web` vendor 了 three.js 与 `GLTFLoader`，
   只差一个 `AnimationMixer`（约 30–50 行）〔实测〕。**工作量**：解析 2–3 人日 + GLB 写出 1–1.5 + 编辑器 0.5 +
   Unity 验证 0.5–1，合计 **4–6 人日**（不含状态机与美术核对）；首刀（3 种螃蟹）已按这个量做完，见 §11。

## 2. 绑定姿势与骨骼层级

动画块里有两张平行的 u32 指针表：

1. **物件动画表**在块内偏移 `0x75FC0`（RAM `0x482FC0 − 0x40CC00`）：`u16` 表项数（**实测 249**），随后是相对该表基址的 `u32` 偏移数组。
   表项：`+0x00` 剪辑数 `u16`、`+0x02` objectId `u16`（不匹配就跳过）、`+0x04` 起每条剪辑 4 字节 = `速度档 u16` + `曲线组号 u16`。
2. **绑定姿势指针表在块的最开头**（块内偏移 `4 + 4i`，`i` = 表项序号）——注意它不嵌在表项里；
   实测 entry 0 指向 `0x3F0`，在那里读到 `partCount=7` 且层级自洽〔实测〕。**这是移植时最容易踩空的一处。**

绑定姿势块格式〔实测〕：

| 偏移 | 类型 | 含义 |
|---|---|---|
| `+0x0A` | u16 | 骨骼（部件）数 |
| `+0x10` | — | 第 0 条起点，随后每条 **0x20 字节** |
| `+0x00` | f32×3 | 相对父的位置（**米**，见 §5 的单位说明） |
| `+0x0C` | u8 | 部件序号（必须 == 数组下标） |
| `+0x0D` | u8 | 父序号 **+1**（0 = 无父）；必须 < 自己 |
| `+0x10` | f32×4 | 四元数 (x,y,z,w)，**w 取负读取** |

层级不是树而是**拓扑序数组**：父下标恒小于自己（参考实现直接断言这一点），所以一次前向遍历即可算出每个骨骼的世界参考矩阵
= 父参考矩阵 × T(pos)·R(rot)。Cancer 的 19 个类型里骨骼数 2–12，最深链 4 层〔实测〕。

## 3. 蒙皮：矩阵调色板，不是逐顶点权重组

任务包里每个物件占 11 个连续扇区（LOD0/LOD1/LOD2/纹理/CLUT/碰撞/…）。**只有带动画的物件**才走 LOD1：

- LOD0 是一个整体的远景块；**LOD1 才是分部件的真模型**，而蒙皮表就压在 LOD1 扇区头与部件扇区之间。
- 从 `lod1 + 0x10` 到「`lod1 + u32(lod1)`」之间是调色板表，每条 **0x20 字节**：

| 偏移 | 类型 | 含义 |
|---|---|---|
| `+0x00` | s8×4 | 四个关节号（骨骼下标），`-1` = 空位 |
| `+0x04` | u8×4 | "配对索引"：指向上面四个关节号之一 |
| `+0x0D` | u8 | 配对数（0–4） |
| `+0x0E` | u16×4 | Q15 权重（`/32768`） |

- 每个部件模型头 `+0x1C` 有一个 `u8` 骨骼号（**这个部件刚性跟哪根骨**）；顶点流里位置的 `W` 分量低 8 位
  （`(W>>2)&0xFF`）是**调色板槽号**。
- 语义〔实测 + 推断〕：调色板槽不是"每顶点最多 4 个权重"，而是"**一个输出矩阵**"——「部件刚性矩阵」与「关节矩阵」按槽内
  权重插值，顶点用槽号选一个矩阵（渲染端只有一个 `mat3x4` 数组 + 一个整数索引）。
- **Cancer 实测分布**（19 个类型、91 个槽）：**83 槽 0 影响（纯刚性）、6 槽单关节、2 槽双关节**；
  权重只出现 1.0 和 0.5 两个值；双关节的两个槽都在 **Lalala（objectId 1695，12 骨 7 部件）** 上，且两个权重都是 1.0
  ——也就是说参考实现那里的结果是"按顺序做矩阵插值"，最终完全落在第二个关节上。
- **槽数 ≠ 骨骼数**：Sparrow(525) 2 骨 1 槽、Snoozing Momma(529) 4 骨 3 槽、Lalala 12 骨 7 槽〔实测〕。导出时不能假设一一对应。

> 结论：**Cancer 的道具本质是"刚性分部件骨架"**（部件数 91、骨骼最多 12）。真正的平滑蒙皮在原作里只出现在极少数道具上。
> 这对导出是好消息：GLB 的 `JOINTS_0/WEIGHTS_0` 按"每部件 1 个骨骼、权重 1"就能 99% 还原。

## 4. 动画剪辑：曲线、采样、插值

**剪辑表**（§2 的每类型条目）给出 N 条剪辑，每条 = `(速度档, 曲线组号)`。曲线组表在块内偏移 `0xAB40`（RAM `0x41B740`），
同样是「u32 相对偏移数组」，索引 0 是空槽。

**曲线组头**〔实测〕：`+0x00` 段数 `u16`、`+0x02` 曲线数 `u16`、`+0x04` 段长 `u16`（除以 `0xA0`；**全库 2,354 条剪辑实测恒为 1.0**）、
`+0x07` 是否相对 `i8`、`+0x08` 起一条 `u16` 偏移表（相对曲线组头，末条长度到组尾）。每条曲线是独立数据块，
长度由"下一条偏移"推出——**没有显式的块长度字段**，这是移植时第二处容易踩空的地方。

**每条曲线头**：`+0x00` 部件号 `u8`、`+0x01` 标志位 `u8`、位置曲线 `+0x04` 一个 `f32` 缩放。
标志位：低 2 位 = 分量号（0/1/2 = x/y/z，3 = 四元数 w）；`0x0C` = 位置、`0x08` = 旋转（二者互斥，必须有其一）；
`0x10` = 线性、`0x20` = 阶梯（**数据里未使用**，参考实现断言为 0）、`0x40` = 稀疏、`0x80` = 二进制（未使用）。

| 曲线种类 | 载荷 | 插值 |
|---|---|---|
| 样条（默认） | 段边界数组（段数 < 0x100 用 u8，否则 u16）+ int16 值数组 + int16 切线数组 | Hermite（切线与段长、段长/间隔比相关；旋转的切线系数是位置的 2 倍） |
| 线性（`0x10`） | int16 × 段数 | 段内线性 |
| 稀疏（`0x40`） | 每段 1 bit 的掩码（首 bit 必须为 1）+ int16 值数组（变化段数 + 1） | 变化段内线性，其余保持 |

- **值的单位**：位置 = int16 × `f32 缩放`；旋转 = int16 × `1/32768`，且分量 3（w）**取负**。
- **时间轴**：帧号 → 段号 = `帧 / 段长 + 1`；循环区间 = `段长 × (段数 − 1)` 帧（整条剪辑无缝循环，**没有独立的循环标记**）。
- **播放速率**：`fps = (速度档 u16 ÷ 256) × 30`。实测速度档的取值集合
  `{0, 0.297, 0.5, 0.797, 1.0, 1.199, 1.297, 1.398, 1.5, 1.598, 2.0, 2.297, 2.5, 3.0, 3.5, 4.0, 4.5, 5.0, 10.0, 15.0}`
  ——**速率 0 = 冻结**（`fps=0` 时帧号恒为 0，只摆一个姿势；全库 15 条，Cancer 里 6 条，例如 Pigeon(141) 第 1 槽、Toy Dog(526) 第 1/3 槽）。
- **两种模式**：`是否相对` 为真时，曲线值是**叠加在绑定姿势上**的增量（先清零再累乘绑定姿势）；为假时曲线值就是绝对局部 T/R。
  Cancer 的 19 个类型里 **11 个至少有一条相对模式的剪辑**，而且通常只出现在个别槽上（例如三只螃蟹的第 2 槽）〔实测〕。
- **剪辑长度**（`段长 × (段数−1) / fps` 秒）〔实测〕：Cancer 的 87 条主体是 30 段；速度 1.0 的 30 段 = **0.967 s**，
  速度 2.0 = 0.483 s，速度 3.0 且 10 段 = 0.100 s（短促动作，例如"甩一下/抖一下"）。

**没有 `playAnimNo` 这个字段名**：参考实现的剪辑选择完全是运行时的——`objects.ts` 的 `AnimationType`
`{IDLE=0, MOVING=1, WRIGGLE=2, PANIC_A=3, PANIC_B=4, UNK5=5}` 经静态置换 `[3,0,2,1,4,5]` 映射到剪辑下标
（`setAnimation`，L198–L209），播放器是 `AdjustableAnimationController`（`BanjoKazooie/render.ts`，`init(fps)` 把上面的 fps 灌进去）。
`playAnimNo` 只存在于 REROLL dump 的逐实例列里（§5）。**PS2 的 0x40 字节实例记录里没有等价字段**〔实测：
524 条里唯一可疑的 `+0x08` 字节全为 0，而 dump 里 Cancer 的取值是 −1:371、0:118、1:34〕。

- **读法 B**：它就是剪辑数组的原始下标（0/1），与 IDLE/MOVING 无关。差别只在"开局播哪条"，两种读法下其余逻辑相同。

## 6. 我们自己的提取器：现状与缺口

`~/KatamariRef/tools/katamari_stage_extract/`（约 1,600 行，含运动表解码）已经有：
`layout.py`（ELF 块地址表，**已含 animationBlock 范围**）、`mission.py`（关卡表、0x40 记录、父表、随机组、区）、
`stage.py`（舞台 BIN 的扇区→模型→VIF→顶点/索引/材质段；模型头 `+0x1C` 的骨骼号已经读出来叫 `anim`；
顶点里已经保留 `(W>>2)&0xFF` 的调色板槽号）、`glb.py`（静态 GLB 写出）、`__main__.py`（CLI）、`decode_motion_tables.py`。

缺的就是本文 §2–§4 的三块：

| # | 缺口 | 可复用 | 估计行数 |
|---|---|---|---|
| a | `objectBlock` 的 `animated`（`+0x1A`）/`dummyParent`（`+0x21`）标志 | 无 | ~15 |
| b | **任务包内嵌物件模型**：`0x04 + (0x09+id×0x0B)×4` 的 lod0/lod1 指针 → lod1 → 调色板表 → 部件扇区 | `stage.parse_model_sector` / `parse_model` 直接可用（它们只吃"缓冲区 + 偏移"） | ~80 |
| c | **动画块**：物件动画表 + 绑定姿势表（块首 u32 数组）+ 曲线组 + 三种曲线解码 | 无（唯一的新格式） | ~250 |
| d | **GLB skin + animation 写出**：skin/`JOINTS_0`/`WEIGHTS_0`/`inverseBindMatrices`、骨骼节点树、逐剪辑逐骨采样器 | `glb.py` 的 accessor/bufferView 设施 | ~200 |
| e | 打包约定：每类型一份资产 + `instances.json` 的 t/q/s 挂实例 | `instances.json` 已有 t/q/s | ~40 |

**导出流程**（已按此实现）：本关实例表 → animated 集合 → 每类型：lod1 扇区 → 部件网格（每部件一个 primitive，
带骨骼号与槽号）+ 动画块绑定姿势（父链 → 节点树）+ 剪辑表 → 曲线组 → 按 fps 逐帧采样成逐骨 TRS →
一份 GLB（1 个 skin + N 部件 primitive + K 条 animation）；实例只引用该类型的 GLB。

**核心难点是"重采样"**：原作按分量存 int16 + Hermite/稀疏位掩码，glTF 只认"每通道关键帧 + LINEAR/STEP"，
不能直搬，必须按 `fps = 速度档×30` 逐帧求值并归一化成四元数（30 段剪辑 = 30 帧关键帧，体积很小）。

## 7. 速率与时长：回答"播放速率是否已知"

- **数据侧已解**：fps 与段长都是表里的字段（§4），Cancer 87 条剪辑的速率全部算得出来；**M5 的"fps/循环区间"这半结案**
  （循环区间 = 整条剪辑，`段长×(段数−1)` 帧）。
- **仍属〔推断〕的是"原作是否真按这个 fps 播"**：这是参考实现的读法（它把 `速度档×30` 直接喂给一个按秒累加的播放器）。
  自洽性证据：30 段 @1.0 = 0.967 s，与观察到的"螃蟹步态 ≈1 s 周期"同量级；同组曲线用 1.0/2.0/3.0 三档播，
  正好对得上"同一种走法、大小不同、快慢不同"的观感。
- **M5 的另一半（IDLE↔MOVING 何时切）仍是行为问题**，不在数据里，需要运动程序侧（`ORIGINAL_MOTION_PROGRAM` §M5）或实机观察。

## 9. 风险与未知项

1. **`playAnimNo` 语义未定**（§5 读法 A/B）：只影响"开局播哪条"。要定案得看实机或 PS2 代码。
2. **哪条剪辑是"走"没有代码级证据**：螃蟹 slot0 与 slot3 时长同为 0.967 s、曲线不同；本文按"周期 + 腿摆幅度 + 身体起伏"
   定性（slot0 腿摆 ±15° = 走、slot3 ±5° + 0.76 cm 起伏 = 待机），与参考实现反推的 `[3,0,2,1,4,5]` 独立吻合【推断，强】。
3. **调色板权重的语义是参考实现的解释**（"按序做矩阵插值"，权重不归一）：实测只有 1.0/0.5；重复关节的槽与顺序无关，
   只有 Lalala 的两个双关节槽依赖顺序。导出按"每部件刚性 1 骨 + 双关节槽按后者优先"处理（§11），接受这 1 件道具的差异。
4. **重采样会改变曲线形状**：Hermite/稀疏插值在 glTF 里只能线性烘焙；螃蟹实测最大角误差 0.085°（§11），其余类型要复核。
5. **骨骼数 ≠ 部件数**（§3）：导出必须以 `animationIndex` 与调色板映射为准，不能按"第 i 部件 ↔ 第 i 骨"。
6. **`是否相对` 两种模式必须分开处理**：绝对模式直接用曲线值，相对模式先清零再叠绑定姿势，弄反会得到"双倍旋转"。
7. **动画块只覆盖到 `0x386C54`；少数关卡缺蒙皮数据**（参考实现有补丁列表，等于"假装不动画"），换关要重跑并核对。
8. **30 Hz 时间基准 + 合规**：glTF 时间轴是秒，Unity 导入别开"优化/压缩"，否则关键帧被合并、姿态会漂；
   解析器、探针、产物全部在仓库外，仓库许可未定前不放"派生自参考实现"的代码进来（`NOCLIP_KATAMARI_FORMAT` §10）。
9. **未验证**：`速度档=0` 的 15 条剪辑在原作里是"冻结"还是"由游戏代码改速率"（参考实现是冻结）。

## 11. 实现与首刀验证（3 种螃蟹，2026-11-16）

按 §6 的流程实现，四块**全部在仓库外**（`~/KatamariRef/tools/katamari_stage_extract/`）：`props.py`（任务包内嵌物件模型 +
调色板）、`animation.py`（动画块解码 + 采样 + 逆绑定矩阵）、`glb.py` 扩展（skin / IBM / 逐剪辑 animation）、
`build_props.py`（CLI）。部件网格仍走 `stage.parse_model_sector`，**没有第二套解析**；校验脚本 `~/KatamariRef/tools/check_prop_glb.py`。

- **产物**：`~/KatamariRef/props/skinned/type_{480,481,482}.glb`，各 **67,400 / 67,396 / 67,388 B**（构建可复现，md5 稳定）——5 骨、5 部件
  （body 218 顶点 + 4 条腿各 76）、522 顶点、789 三角形、5 条剪辑。根节点矩阵 `diag(0.01, −0.01, −0.01)`
  （厘米→米 + 绕 X 转 180°），与那 1,703 个静态 GLB 的约定一致，可直接替换同名静态模型。
- **两个必须记住的点**：**(a)** 部件顶点是**骨骼局部坐标**，写 GLB 前要先乘该部件的绑定世界矩阵（glTF 蒙皮要 bind 空间）
  ——漏了会炸成尖刺（第一版实测如此）；**(b)** 每部件 1 primitive、每顶点 1 骨权重 1，IBM = 绑定世界矩阵之逆。
- **重采样偏差【实测】**：导出关键帧的线性插值与源曲线在**帧间中点**对比，最大角误差 **0.085°**、位置误差 **0.000 cm**；
  循环以 `maxFrame` 为周期，首末帧姿态差 ≤0.4°（源数据量化残差）。
- **剪辑命名**：PS2 槽号按 REROLL `resources.assets` 的 `mononame.ANIM_NAME` 对应原作状态：slot0 `walk`、slot1 `escape`、
  slot2 `rampage`、slot3 `idle`、slot4 `chase`、slot5 `special`（对照与证据见 [MOTION_HOST](../../Design/PickupAbsorb/MOTION_HOST.md)
  「骨骼动画：普通 Animator」）。这三型螃蟹测得：walk 30 帧/0.967 s，腿摆 ±15°；escape 0.483 s，同动作 2×；rampage 0.1 s
  ±30° 快抖（相对模式）；idle 0.967 s，±5° + 0.76 cm 起伏；chase 与 walk 同曲线。
- **视觉验证**（无头 chromium + 仓库里 vendored 的 three r186；截图在 `~/KatamariRef/props/shots/`）：
  `strip_walk.png`（6 相位）、`strip_idle.png`（4 相位，几乎静止）、`strip_relative.png`（相对模式 + Coconut Crab）、
  `cmp_noclip_vs_ours.png`（上排 noclip 3 帧 / 下排我们 3 相位）。**腿在动、身体没炸、朝向与静态包里同种螃蟹一致、
  三种螃蟹比例各自正确、相对模式没弄反**（弄反会双倍旋转）。`check_prop_glb.py` 三文件全 ok
  （骨索引合法、权重和 =1、IBM 非奇异、时间轴单调、只用 LINEAR）。
- **FBX 转换【实测】**：`Tools/levelbuild/blender/skinned_glb_to_fbx.py` 出的 FBX 静止姿态尺寸与静态模型一致（单位、轴向、bind 姿态都对，三型差 ≤0.0001 m）；take 名按 Blender 导入后的动作名（`<clip>_root`）去后缀后查剪辑表，三型的 `walk/escape/rampage/idle/chase` 时长为 0.9667/0.4833/0.1/0.9667/0.9667 s，与 `report.json` 一致。`SkinnedMeshRenderer.bounds` 覆盖全部剪辑姿态且处于倾斜约 8° 的根骨坐标系中，约为静止模型的 1.17×1.27×1.17，不能当模型尺寸用。
- **FBX 帧率【实测】**：FBX 的 `TimeMode` 就是 Unity 剪辑的采样率，Unity 把 take 取整到该帧率的整帧。源剪辑的秒数是 29/30（0.9667）、29/60（0.4833）、9/90（0.1），在 Blender 默认 24 fps 下不是整帧：烘焙只打到整数帧（关键帧末点 0.9583 s，24 帧），Unity 读成 23 帧 = 0.9583 s、escape 0.4583 s。转换脚本把场景帧率设为使全部剪辑为整帧的最低值（`scene_fps`，这三型是 60：58 / 29 / 6 帧），导入 glTF 前设置，导出的 FBX `TimeMode` 为 60 fps，关键帧末点 0.9667 / 0.4833 / 0.1 s。`skinned_defs.json` 记 `fps`，装配器在导入后核对每条剪辑的长度。
- **螃蟹与地面【实测，离线】**：`placement.v2.json` 的 120 只螃蟹（`position` = 静态模型 AABB 中心）对接触地形 `.katerrain`：静态底面相对地面，71 只在 ±3 cm 内，9 只低于 3 cm 以上（最低 −6.9 cm），其余在家具/其他道具上；按运动类，hop 中位 −1.4 cm、路径类 −1.75 cm、游走类 +0.3…+1 cm。静态模型的底部即原作数据里的位置，蒙皮模型的 bind 底部由装配器按 bounds 中心对齐到同一高度（蒙皮 bind 包围盒中心相对其原点偏 −0.6 cm / 0 / +0.9 cm，对齐后抵消），所以"蒙皮 pivot 偏移"与"原作埋地"都不是大面积埋地的原因。动画姿态相对 bind 最低点：type_480 抬高 1.1–1.2 cm，type_481 下降 0–1.0 cm，type_482 下降 2.1–4.3 cm。接触地形与视觉网格在部分位置不重合（`small_fiddler_crab_056` 处接触面 −1.378，视觉面 −1.133），按"地面高度"测量时取哪一张网格会差到 0.25 m。
- **路径类的 y【实测】**：路径点落在接触地形上（p23：与地面差 −1.5…+2.7 mm），螃蟹出生中心在路径点之上约一个半高（10 个路径件中 9 个，0.5–1.1 cm 以内）。路径点已换成项目世界；`MotionMath` 只转换原作的中心相对位移 `(0, −b, 0)`，因此中心落在 `point + (0, b, 0)`，宿主与预览都不另行抬升。
- **局限**：与 noclip 的对比是**姿态级**（现成截图里螃蟹仅约 90 px）。逐姿态对比要起 noclip dev server + 装
  `playwright-core`（都在仓库外），没做，是可选的验证项。
