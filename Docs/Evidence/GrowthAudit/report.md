# 第一关（story_01_bench_size）成长手感审计 — 数字与结论

> 只读审计（2026-11-15）。所有数字由 `/tmp/growth_audit/audit.py`、`scenarios.py` 从 `Docs/Design/Levels/story_01_bench_size/placement.json`（127 props / 44 defs / 1500 u）与 `KatamariBallMotor.cs` / `SizeModelMath.cs` / `PickupAbsorbMath.cs` 的常量算出。没有跑 Unity、没有 Play Mode、没有改任何 tracked 文件。

## 0. 结论摘要

1. **门槛本身是自洽的**：`D_req=(60abc/π)^(1/3)` 使 `V_ball(D_req) ≡ 10·V_box`。若成长也按物理体积走，单次吸收最多 +10% 体积（+3.2% 直径）。
2. **成长量与门槛用的不是同一个量**：成长 = `valueUnits × 0.0041 m³`，而 value 是按档位定的整数（1/4/6/8/12/16/32/36/38/52/64/90/120/130/150/212），不是按体积。全关 `ΣV_val=6.15 m³` vs `ΣV_box=2.517 m³` → **整体放大 2.44×**，单 def 从 0.24× 到 **2288×**。
3. **开局池**：`D=0.2997` 时已经有 **87/127 件（68%）** 可吸，合计 **264 u = 1.082 m³ = 起始球的 76.8×**；全吃掉（按 value）球从 0.30 → **1.28 m**。这是「前 30 秒吃掉整关 2/3 物件」的来源。
4. **单次冲击**：44 个 def 在「首次可吸直径」处的中位数是 **+39% 体积（+11.6% 直径）**；最坏是 4 u 小件在开局被吃：**+116% 体积（+29.3% 直径）**。按门槛的 10% 口径，43/44 个 def 超标。
5. **用户的 0.5→0.6 例子**：等价于一次 **12 u** 吸收（+0.0492 m³）。全关唯一 12 u 的 def 是 `serving_tray`，门槛 `D_req=0.528`，实际是 **0.528 → 0.622（+17.9% 直径，+63.9% 体积）**；正好 0.50 时没有 def 能到 0.58（最大是 8 u 的 `book_stack` → 0.573）。
6. **用户算术成立的部分**：代码里同一物件永远加 `valueUnits×0.0041`，与球多大无关（体积守恒的是「价值体积」，不是物理体积）。所以不存在「D=3.5 时同一物件加 2 m³」。真正被放大的是 **value 体积相对物理体积**，而且起始球只有 **3.44 u**，所以 **1 u = 起始球的 29%**——这是整数的粒度下限。
7. **还有一个内容侧硬伤**：如果成长真的改用物理体积（k=1），本关会在 **D=0.581 卡死**（下一件 `wood_plank` 的 0.01225 m³ 需要球 0.1225 m³，而全关 0.581 以下的可吸物件只有 0.089 m³）。要吃完 127 件走到 2.20，成长系数至少要 **2.80**。
8. **推荐**：把成长量从 value 换成 **物理体积 × 常数 k≈2.8**（方案 C），单次冲击上限从 +29.3% 降到 **+8.5% 直径**，且 2.20 m 仍然可达。代价是 score 与体积解耦、账本要记第二根量。

## 6. 用户的 0.5→0.6 例子复现

* 0.50 的球 V=0.06545 m³；要到 0.60（V=0.11310）需要 **+0.04765 m³ = 11.62 u**。value 必须是整数，所以对应 **12 u = 0.0492 m³**，结果 D=**0.6027**（用户把它读成 0.60，再由 0.60 反算出 +0.048，所以那个 0.0477 是回算值，不是代码输出）。
* 全关唯一 12 u 的 def 是 **`serving_tray`**（0.55×0.04×0.35，`D_req=0.528`）。在门槛处吃它：V 从 0.0770 → 0.1262，D **0.528 → 0.622（+17.9% 直径 / +63.9% 体积）**。这就是用户看到的那一跳（报成 0.5→0.6）。
* 在**正好 0.50** 那一帧，没有任何 def 能到 0.58：可吸的最大 value 是 `book_stack` 8 u，0.500 → 0.573（+14.5%）。其次是 6 u 的 `watering_can`（0.500→0.545）。
* 所以：他的**数值方向对、数值略大**；真实机制是「12 u 的托盘在 0.528 被吃」，不是「任何物件在 0.5 都会 +73%」。
* 题外但重要：0.50 之前球只吃了 13 件（13 u），说明他只吃了 1 u 小件；一旦先吃 4 u 小件，开局就是 0.30→0.386 的一跳。

## 7. 用户的算术点成立吗？

**成立的部分（代码事实）**：`V=(baseline+Σu)·c`，`DeriveSize` 只读累计 units，所以**同一物件永远加同样的体积**（`u×0.0041`），与球多大、与 D 无关；`D=3.5` 超过 2.20 的硬上限，运行时不存在那一档，更不存在「同一物件加 2 m³」。相对涨幅随 D³ 下降，所以模型本身**不是**加速膨胀。

**真正的放大在别处（测得）**：

1. **value 体积 vs 物理体积**：`ΣV_val/ΣV_box = 2.44×`；per-def 0.24×–2288×。门槛问的是物理体积（`V_box ≤ V_ball/10`），成长给的是价值体积，两个量只靠一张按档位定的表连接。
2. **整数粒度 / 起始球太小**：起始球 = 3.44 u，所以 **1 u 就是起步体积的 29%**。任何 ≥1 u 的物件在开局都是一次 29%+ 的跳；4 u 档是 116%。这是「0.5→0.6」那类跳的机制。
3. **开局池太宽**：87 件可吸、264 u，是起始球的 77 倍——玩家前 30 秒能把整关 68% 的物件扫掉。
4. **内容与 2.20 m 目标不自洽**：`LEVEL_CONSTRUCTION.md:198` 自己算过「412 u 只到 1.482 m，要到 2.20 需 1356 u，是 3.3 倍」，决定 (q) 的解法是给 17 件结构件 1088 u。**价值单位是为了凑到 2.20 而被抬上去的，物理体积没变**——于是球每吃一件都比它吃掉的物理体积大 2.44 倍。

一句话：**不是「同一物件越吃越多」，是「同一物件被标价标得比它自己大 2.44 倍，而且最小标价单位（1 u）就是起步球的 29%」。**

## 8. 三个修法（含对本曲线的数值影响）

### A. 把 valueUnits 改成由物理体积导出（并按需要补件）

`u_i = max(1, round(V_box_i × k))`。要维持 1500 u，`k = 1500/ΣV_box = 596 u/m³`，等于每件按体积定价、整体仍放大 2.44×（与今天的 2.44× 同量级，但不再有 0.24×–2288× 的离群）。**效果**：门槛处单步变成统一的 **+24.4% 体积（+7.6% 直径）**，但 **开局 1 u 夹取仍在**——模拟仍出现 29.1% 的首步，且 124 次后停在 1.84 m（顶部 3 件吃不到）。若改成严格守恒（k=1，带 1 u 夹取后总 699 u），开局池只到 0.42 m，随后在 **0.58 m 卡死**（内容体积阶梯有断档）。

**优点**：一次性消掉「小件标价 100×」的荒谬；value 与体积同向，设计师可解释。

**缺点**：整数夹取让开局仍有一跳；守恒版需要补 **约 3 m³** 物理内容才够 2.20（现 2.52 m³）；等于重写 44 个 def 的 value + 加物件。

**改哪里**：`Docs/Design/Levels/story_01_bench_size/placement.json` 的 `defs[].valueUnits`、`Tools/levelbuild/placement_core.py`（校验 volume→value 的推导）、`Editor/Pickup/PickupFieldSync.cs`（只消费声明值，已具备）、`Docs/Design/StoryMode/PROP_SET_PLAN.md`（价值表）。

**设计师要做什么**：给 44 个 def 逐个按 AABB 体积写整数分；再补 2–3 m³ 的中大件把 2.20 填满。

### B. 保留 value 表，改体积换算 / 起始球 / 上限

`c` 是**尺度中性**的：`c` 从 0.0041 改到 0.002，起始球和每单位体积同时缩小，所有相对跳跃不变（只是 0.30 m 变成 0.24 m）。所以能动的只有 **起始球（baselineVolumeUnits）** 与 **上限**。把起始抬到 **40 u**（D=0.679 m），4 u 件才降到 10% 体积（+3.2% 直径）；但 0.30–0.68 这段早期内容整段消失，可玩直径区间从 7.3× 压到 3.2×。若只抬到 10 u（D=0.428），4 u 件仍是 40%（+11.9%）。

**优点**：不动 127 件数据、不动 score；一个序列化字段 + 关卡 JSON。

**缺点**：治不了中后期（4 u 之外的档位仍按档位定价）且会让尺寸门几乎失去排序作用；起始球一改，`layout.json`/`placement.json` 的 `ballDiameterStart`、所有 `size_gates` 门槛、挡路窗口、星级带全部要重算，牵动面比 A/C 都大。

**改哪里**：`KatamariBallMotor.cs` 的 `baselineVolumeUnits` / `maxCoreRadiusWorldM`、`StoryMode.unity` 里的序列化覆盖、`placement.json` 的 `level.ballDiameterStart/Max`、`Docs/Design/Maps/PicnicLawn/layout.json` 的 `size_gates`。

**设计师要做什么**：重新验一遍所有 gate bench / 花圃台阶的开启球径和星级目标。

### C. 让成长量与价值脱钩：按物理体积 × 常数 k 成长（推荐）

`ΔV = k × V_box`。关键恒等式：**在门槛处被吃时，单次涨幅 = k/10**（因为 `V_box = V_ball/10`），与物件大小无关——这就是「均匀」。今天的对应量是 `inflation/10 = 0.02～229`。

* `k = (V_cap−V0)/ΣV_box = 2.21` 是「全关体积 × 2.21 = 满径体积」的比值，但按它模拟会在 **1.73 m 停住**：`stroller`(0.55 m³)/`folding_table`(0.42)/`lounge_chair`(0.336) 这三件太大，剩下 124 件凑不到它们的门槛。
* `k = 2.80` 是「吃完 127 件刚好到 2.20」的最小值（二分求得）：每次门槛吸收 **+28.0% 体积 / +8.5% 直径**，全程没有更大的跳；中位数从今天的 +39% 降到 +19%，最坏从 +116% 降到 +28%。
* k 的阶梯（都按「门槛处涨幅 = k/10」）：`0.8`→停在 **0.52 m**、`1.0`→**0.58**、`1.4`→**0.77**、`1.8`→**1.20**、`2.0`→**1.46**、`2.21`→**1.73**、`2.80`→**2.20**。**k 能取多小，完全由内容体积阶梯决定**——不是调参口味。

**优点**：唯一能在「起始 0.30 + 整数 score」都不变的前提下把最坏冲击压到 +8.5% 的方案；门槛和成长终于用同一个量（`V_box`），门槛的 10× 从口号变成「单步上限 = k/10」的保证；形状与原作「物件体积 × 比例」一致（S-AR01，比例 0.8<1）。

**缺点**：score 与尺寸解耦，账本要多记一根「确认体积」（Udon 下是新增字段 + 事件字段，不是小改）；要真正做到「原作的 8–10% 步长」（k≈1），得把体积阶梯填密：5–12 L 那一档现在只有 `wood_plank`（0.01225 m³）一件，顶部 0.3–0.55 m³ 只有 `lounge_chair`/`folding_table`/`stroller` 三件；节奏后移——0.30→0.50 要 76 次吸收（今天 13 次），1.25 m 的 1 星要 117/127 件（今天 83 件/248 u），1.45 m 要 120 件、1.60 m 要 122 件。

**改哪里**：`PickupAbsorbMath.cs`（`V_box` 已有，加一个 `ΔV` 的纯函数）、`KatamariBallMotor.cs`（`CommitAcceptedAbsorbs` / `DeriveSize`、序列化 `growthRatioPerBoxVolume`）、`GrowthLedgerMath.cs`（事件里记确认体积、总账加一列）、`SizeModelMath.TryDerive`（改成读体积）、`Editor/LevelBuild/PlacementImporter.cs` + `placement_core.py`（把 `V_box` 带进运行时）、测试 `AbsorbSizeGateTests` / `GrowthLedgerMathTests`。

**设计师要做什么**：仍然只写 `aabb` 与 score 的 `valueUnits`（两者不再互相约束）；额外补 1–2 件 0.3–0.6 m³ 的中大件（或把 `stroller` 拆成两件）让顶部阶梯连续；补约 1.5 m³ 中件（并且按阶梯分布）后，k 才可能降到 1.4。

**推荐 C，5 行理由**：

1. 用户感到的是**单步跳变**，不是平均速度；只有把成长量换成物理体积才能让每一步都落在门槛的 10% 语义附近。

2. A 受整数 1 u 夹取所限，开局仍有 29% 一跳；B 只能靠改起始球，会连带作废所有 gate/星级数据。

3. C 是三者里唯一「起始 0.30 不动、127 件 value 不动、2.20 仍可达」的组合。

4. 与原作形状一致（原作成长比例是「物件体积 × 比例」，且 0.8<1 是压实；我们现在的 2.44 是膨胀）。

5. 它把门槛的 10× 从「一句口号」变成「成长上限的保证」：`k=2.80` 时单步 ≤+8.5% 直径。

## 9. 测得的 vs 推断的

**测得（脚本可复现）**：全部 def 表、`ΣV_box/ΣV_val`、`D_req`、`gain`、`dD/D`、贪心曲线、各方案的模拟数字、开局池 87 件/264 u、`serving_tray` 0.528→0.622。

**代码事实（读过源码）**：`V=(baseline+u)c`；`DeriveSize` 不读 D；门槛 `a·b·c ≤ (π/6)D³/10`；`baseline=3.4390244`、`c=0.0041`、`cap=1.1`(core)；127 件 aabb 来自 manifest；第一关无 `@size=`。

**推断（可能有错）**：① 玩家实际滚序接近「就近吃」，所以 §4 的最坏冲击比 §5 的贪心曲线更接近体感；② 原作成长比例 0.8 只来自一份社区数据挖掘（S-AR01 附带表），**本轮没有核验**；③ `k=2.80` 是「吃完 127 件刚好到 2.20」的最小值，是算出来的，不是设计值；④ 开局池 87 件是否真的能在 30 秒内全部够到，取决于 reach/吞吐/地形，本文按题设忽略几何。

**没有验证**：Unity/Udon 编译、Play Mode、VR、网络；本文没有任何运行时证据。
